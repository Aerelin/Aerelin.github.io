## 第一部分：QEMU

### 1. QEMU 简介

QEMU 是一款开源的**模拟器**及**虚拟机监管器**（Virtual Machine Monitor, VMM）。

QEMU 主要提供两种功能给用户使用：

| 功能 | 说明 |
|------|------|
| **用户态模拟器** | 利用动态代码翻译机制（TCG, Tiny Code Generator）来执行不同于主机架构的代码。例如在 x86 主机上运行 ARM 程序。 |
| **虚拟机监管器** | 模拟全系统，配合 KVM 等硬件虚拟化技术实现接近原生的性能。 |

**核心要点：**
- QEMU 是开源项目，官网地址：[https://www.qemu.org/](https://www.qemu.org/)
- 在 CTF Pwn 方向中，QEMU 常用于搭建内核漏洞利用的调试环境（如 `qemu-system-x86_64`）

---

### 2. QEMU 安装

QEMU 有两种安装方式：

#### 方式一：使用包管理工具安装

> 优点：简单快捷。缺点：版本可能较老。

不同 Linux 发行版的安装命令如下：

| 发行版 | 安装命令 |
|--------|----------|
| Arch | `pacman -S qemu` |
| Debian / Ubuntu | `apt-get install qemu` |
| Fedora | `dnf install @virtualization` |
| Gentoo | `emerge --ask app-emulation/qemu` |
| RHEL / CentOS | `yum install qemu-kvm` |
| SUSE | `zypper install qemu` |

#### 方式二：源码安装

> 优点：可以获取最新版本，按需定制编译选项。缺点：编译耗时较长。

以 QEMU 6.2.0 为例：

```bash
# 1. 下载源码
wget https://download.qemu.org/qemu-6.2.0.tar.xz

# 2. 解压
tar xvJf qemu-6.2.0.tar.xz

# 3. 进入源码目录
cd qemu-6.2.0

# 4. 配置编译选项
./configure

# 5. 编译
make

# 6. 安装（可选）
make install
```

**注意事项：**
- 编译前需要确保系统已安装必要的依赖（如 `gcc`、`make`、`pkg-config`、`glib-2.0` 等）
- 如果需要 KVM 支持，编译时需确保系统支持硬件虚拟化并在 `./configure` 时启用

## 第二部分：Linux Kernel 基础知识

### 1. 可加载内核模块（LKMs）

**Loadable Kernel Modules（LKMs）**，即可加载内核模块（或直接称为内核模块），其本质就像运行在内核的可执行程序。

#### 核心概念

- **文件格式**：LKMs 的文件格式和用户态的可执行程序相同
  - Linux 下为 **ELF** 格式
  - Windows 下为 **exe/dll**
  - macOS 下为 **MACH-O**
  - 因此我们可以用 **IDA** 等逆向工具来分析内核模块

- **编译与运行**：模块可以被单独编译，但**不能单独运行**。它在运行时被链接到内核，作为内核的一部分在内核空间运行，这与运行在用户控件的进程不同。

- **常见用途**：模块通常用来实现一种文件系统、一个驱动程序或者其他内核上层的功能。

#### 典型应用场景

```
┌─────────────────────────────────────────┐
│              Linux Kernel               │
│  ┌───────────┐  ┌───────────┐          │
│  │ 文件系统   │  │ 驱动程序   │  ← 内核模块 │
│  │ 模块       │  │ 模块       │          │
│  └───────────┘  └───────────┘          │
│  ┌───────────┐                         │
│  │ 网络协议   │  ← 内核模块              │
│  │ 栈模块     │                         │
│  └───────────┘                         │
└─────────────────────────────────────────┘
```

### 2. 内核模块管理命令

Linux 提供了以下命令来管理内核模块：

| 命令 | 功能 | 说明 |
|------|------|------|
| `insmod` | 将指定模块加载到内核中 | 直接加载，不处理依赖关系 |
| `rmmod` | 从内核中卸载指定模块 | 模块必须没有被使用才能卸载 |
| `lsmod` | 列出已经加载的模块 | 显示模块名、大小、被引用次数 |
| `modprobe` | 添加或删除模块 | **会自动查找并处理依赖关系**，推荐使用 |

**使用示例：**

```bash
# 查看当前已加载的内核模块
lsmod

# 加载模块（推荐方式，自动处理依赖）
modprobe <module_name>

# 直接加载模块文件（不处理依赖）
insmod <module_file.ko>

# 卸载模块
rmmod <module_name>

# 查看模块信息
modinfo <module_name>
```

**`insmod` vs `modprobe` 的区别：**
- `insmod` 只加载指定的 `.ko` 文件，不检查依赖
- `modprobe` 会读取 `/lib/modules/$(uname -r)/modules.dep` 文件，自动加载依赖模块，更加智能

### 3. 如何进入 Kernel 态

用户态程序进入内核态（Kernel 态）主要有以下三种途径：

#### (1) 系统调用（System Call）

用户程序通过系统调用主动请求内核提供服务，这是最常见的进入内核态的方式。

```
用户程序 → 触发系统调用（如 read/write/open/ioctl）→ 进入内核态 → 内核处理 → 返回用户态
```

常见系统调用：`read()`、`write()`、`open()`、`ioctl()`、`mmap()` 等。

#### (2) 产生异常（Exception）

当 CPU 执行指令时发生异常（如除零错误、缺页异常、访问违例等），会自动陷入内核态进行处理。

```
用户程序执行 → 触发异常（如 Page Fault）→ CPU 自动切换到内核态 → 异常处理程序 → 返回用户态
```

#### (3) 外设产生中断（Interrupt）

外部设备（如网卡、键盘、定时器等）通过硬件中断信号通知 CPU，CPU 暂停当前执行，切换到内核态处理中断。

```
外设产生中断信号 → CPU 响应中断 → 切换到内核态 → 中断处理程序（ISR）→ 返回用户态
```

#### 总结

```
进入 Kernel 态的三种途径：
┌──────────────────────────────────────────────────┐
│  1. 系统调用    → 用户主动请求内核服务            │
│  2. 产生异常    → CPU 执行异常，自动陷入内核       │
│  3. 外设中断    → 硬件设备触发，CPU 响应中断       │
└──────────────────────────────────────────────────┘
```

### 4. 用户态与内核态的切换过程

#### 进入 Kernel 态之前会做什么？

当从用户态切换到内核态时，CPU 和操作系统需要**保存用户态的上下文**：

- **保存用户态的各个寄存器**：包括通用寄存器（RAX, RBX, RCX, RDX, RSI, RDI, RBP, RSP 等）
- **保存执行到代码的位置**：即保存指令指针（RIP/CS），以便内核处理完成后能正确返回到用户态继续执行

这些上下文信息通常被保存在内核栈上。

#### 从 Kernel 态返回用户态需要做什么？

从内核态返回用户态时，需要执行以下关键步骤：

1. **执行 `swapgs` 指令**：切换 GS 段寄存器的值。GS 寄存器在内核态指向内核数据结构（如 `per-cpu` 变量），在用户态指向用户数据。`swapgs` 用于在两者之间切换。

2. **执行 `iret` 指令**：`iret`（Interrupt Return）指令从栈上弹出之前保存的寄存器值，恢复用户态的执行上下文，包括：
   - `RIP`（指令指针）
   - `CS`（代码段选择子）
   - `RFLAGS`（标志寄存器）
   - `RSP`（栈指针）
   - `SS`（栈段选择子）

> **重要前提**：栈上需要正确布置好恢复的寄存器的值。如果栈上的值被篡改（如内核漏洞利用中的栈溢出），`iret` 返回时就会跳转到攻击者控制的地址，从而实现提权。

**iret 返回时栈的布局（从栈顶到栈底）：**

```
栈顶（低地址）
┌──────────┐
│   RIP    │  ← 返回后执行的指令地址
├──────────┤
│   CS     │  ← 代码段（用户态通常为 0x33）
├──────────
│ RFLAGS   │  ← 标志寄存器
├──────────┤
│   RSP    │  ← 用户态栈指针
──────────┤
│   SS     │  ← 栈段（用户态通常为 0x2b）
└──────────┘
栈底（高地址）
```

### 5. 内核态与用户态函数的对比

相比用户态库函数，内核态的函数有了一些变化。以下是常见的对应关系：

| 用户态函数 | 内核态函数 | 说明 |
|-----------|-----------|------|
| `printf()` | `printk()` | 内核态打印函数 |
| `memcpy()` | `copy_from_user()` / `copy_to_user()` | 内核与用户空间数据交换 |

#### `printk()` 详解

- `printk()` 是内核态的打印函数，对应于用户态的 `printf()`
- **注意**：`printk()` 不一定会把内容显示到终端上，但一定在内核缓冲区里
- 可以通过 `dmesg` 命令查看 `printk()` 的输出效果

```bash
# 查看内核日志
dmesg

# 实时跟踪内核日志
dmesg -w

# 查看最近的内核日志
dmesg | tail -20
```

#### `copy_from_user()` 和 `copy_to_user()` 详解

这两个函数用于在内核空间和用户空间之间安全地拷贝数据：

- **`copy_from_user()`**：实现了将**用户空间**的数据传送到**内核空间**
  ```c
  // 原型
  unsigned long copy_from_user(void *to, const void __user *from, unsigned long n);
  // to: 内核空间目标地址
  // from: 用户空间源地址
  // n: 拷贝字节数
  // 返回值: 未能拷贝的字节数（0 表示成功）
  ```

- **`copy_to_user()`**：实现了将**内核空间**的数据传送到**用户空间**
  ```c
  // 原型
  unsigned long copy_to_user(void __user *to, const void *from, unsigned long n);
  // to: 用户空间目标地址
  // from: 内核空间源地址
  // n: 拷贝字节数
  // 返回值: 未能拷贝的字节数（0 表示成功）
  ```

> **为什么不能直接用 `memcpy()`？**
>
> 内核空间和用户空间使用不同的地址空间映射。直接用 `memcpy()` 访问用户空间地址可能导致：
> - 用户空间页面未映射到物理内存（缺页），直接访问会触发内核崩溃（Kernel Panic）
> - 恶意用户可能传入无效地址，导致安全问题
>
> `copy_from_user()` / `copy_to_user()` 内部会检查地址的合法性，并安全地处理缺页等情况。

### 6. QEMU 启动脚本与 GDB 调试配置

在 CTF Pwn 的内核漏洞利用中，通常使用 QEMU 启动一个精简的 Linux 内核环境，并配合 GDB 进行调试。

#### 修改 `startvm.sh`，加入 GDB 调试选项

以下是一个典型的 QEMU 启动脚本（`startvm.sh`）：

```bash
qemu-system-x86_64 \
    -m 64M \
    -nographic \
    -kernel bzImage \
    -append 'console=ttyS0 loglevel=3 oops=panic panic=1 nokaslr' \
    -initrd initramfs.cpio \
    -smp cores=1,threads=1 \
    -s
```

#### 参数详解

| 参数 | 说明 |
|------|------|
| `-m 64M` | 分配 64MB 内存给虚拟机 |
| `-nographic` | 不使用图形界面，使用串口控制台（ttyS0） |
| `-kernel bzImage` | 指定内核镜像文件（编译后的 Linux 内核） |
| `-append '...'` | 传递给内核的启动参数 |
| `-initrd initramfs.cpio` | 指定初始内存文件系统（包含 rootfs） |
| `-smp cores=1,threads=1` | 配置为单核单线程（便于调试，避免多核竞争问题） |
| `-s` | **开启 GDB 调试**，等价于 `-gdb tcp::1234`，在 1234 端口等待 GDB 连接 |

#### `-append` 参数详解

| 内核启动参数 | 说明 |
|-------------|------|
| `console=ttyS0` | 将控制台输出重定向到串口，配合 `-nographic` 使用 |
| `loglevel=3` | 设置内核日志级别为 3（只显示错误和警告信息，减少干扰） |
| `oops=panic` | 发生 kernel oops 时直接 panic（崩溃），便于调试捕获 |
| `panic=1` | panic 后 1 秒自动重启（防止卡死） |
| `nokaslr` | **关闭内核地址空间随机化**，便于漏洞利用和调试 |

#### GDB 调试流程

```bash
# 1. 启动 QEMU（带 -s 参数）
./startvm.sh

# 2. 在另一个终端中启动 GDB
gdb vmlinux    # vmlinux 是带调试符号的内核镜像

# 3. 在 GDB 中连接 QEMU
(gdb) target remote :1234

# 4. 设置断点（例如在某个内核函数上）
(gdb) b sys_ioctl
(gdb) b my_module_init

# 5. 继续执行
(gdb) c
```

#### 完整的内核 Pwn 调试工作流

```
┌─────────────────────────────────────────────────────┐
│                  调试工作流                           │
│                                                     │
│  1. 编译内核 → 生成 bzImage 和 vmlinux              │
│  2. 制作 rootfs → 打包为 initramfs.cpio             │
│  3. 编写 startvm.sh → 配置 QEMU 启动参数            │
│  4. 启动 QEMU（带 -s 参数）                          │
│  5. GDB 连接 → target remote :1234                  │
│  6. 设置断点 → 分析内核模块漏洞                      │
│  7. 编写 exp → 本地验证 → 远程利用                   │
└─────────────────────────────────────────────────────┘
```

```bash
dmesg -w                       # 实时跟踪内核日志
dmesg -c                       # 查看并清除内核日志
```

### GDB 调试相关

```bash
# GDB 连接 QEMU
gdb vmlinux
(gdb) target remote :1234

# 常用 GDB 命令
(gdb) b function_name          # 设置断点
(gdb) info b                   # 查看断点
(gdb) c                        # 继续执行
(gdb) n                        # 单步执行（不进入函数）
(gdb) s                        # 单步执行（进入函数）
(gdb) p $register              # 查看寄存器值
(gdb) x/20gx $rsp              # 查看内存内容
(gdb) info registers           # 查看所有寄存器
```
