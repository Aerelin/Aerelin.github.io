## 2. vtable 劫持检测机制（glibc 2.24）

在 **glibc 2.24** 版本中，全新加入了针对 `_IO_FILE_plus` 的 **vtable 劫持检测措施**。

### 检测流程

glibc 会在调用虚函数之前首先检查 vtable 地址的合法性：

1. **首先验证** vtable 是否位于 `_IO_vtable` 段中
2. 如果满足条件 → **正常执行**
3. 否则 → 调用 `_IO_vtable_check` 做**进一步检查**

这一机制使得以往直接伪造 vtable 进行劫持的技术变得非常困难。

---

## 3. GLIBC 版本差异对比

### GLIBC 2.23

```c
#define _IO_JUMPS_FUNC(THIS) \
  (*(struct _IO_jump_t **) ((void *) &_IO_JUMPS_FILE_plus (THIS) \
                            + (THIS)->_vtable_offset))
```

在 2.23 中，`_IO_JUMPS_FUNC` 宏直接通过 `_vtable_offset` 偏移获取虚函数表指针，**没有任何合法性校验**。

### GLIBC 2.27

```c
#define _IO_JUMPS_FUNC(THIS) (IO_validate_vtable (_IO_JUMPS_FILE_plus (THIS)))
#define _IO_vtable_offset(THIS) 0
```

在 2.27 中，`_IO_JUMPS_FUNC` 宏改为调用 `IO_validate_vtable` 进行校验，且 `_vtable_offset` 被硬编码为 `0`，进一步限制了攻击面。

---

## 4. IO_validate_vtable 源码分析

`IO_validate_vtable` 是 vtable 检查的核心函数，其源码如下：

```c
void _IO_vtable_check (void) attribute_hidden;

/* Perform vtable pointer validation.  If validation fails, terminate
   the process.  */
static inline const struct _IO_jump_t *
IO_validate_vtable (const struct _IO_jump_t *vtable)
{
    /* Fast path: The vtable pointer is within the __libc_IO_vtables
       section.  */
    uintptr_t section_length = __stop___libc_IO_vtables - __start___libc_IO_vtables;
    const char *ptr = (const char *) vtable;
    uintptr_t offset = ptr - __start___libc_IO_vtables;
    if (__glibc_unlikely (offset >= section_length))
        /* The vtable pointer is not in the expected section.  Use the
           slow path, which will terminate the process if necessary.  */
        _IO_vtable_check ();
    return vtable;
}
```

### 检查逻辑详解

**第一步：计算段长度**

```c
section_length = __stop___libc_IO_vtables - __start___libc_IO_vtables;
```

`__start___libc_IO_vtables` 和 `__stop___libc_IO_vtables` 是链接器脚本中定义的符号，标记了 `_IO_vtables` 段的起始和结束地址。

**第二步：计算偏移**

```c
uintptr_t offset = ptr - __start___libc_IO_vtables;
```

计算 vtable 指针相对于段起始地址的偏移量。

**第三步：判断合法性**

```c
if (__glibc_unlikely (offset >= section_length))
    _IO_vtable_check ();
```

如果 `vtable - __start___libc_IO_vtables` 的 offset **大于等于** `section_length`（即 `__stop___libc_IO_vtables - __start___libc_IO_vtables`），说明 vtable 不在合法的 `_IO_vtables` 段内，调用 `_IO_vtable_check()` 进行进一步处理。

---

## 5. vtable 检查失败的处理流程

当 vtable 指针不合法时，`_IO_vtable_check()` 实际上调用了 `__libc_fatal` 进行输出并退出程序：

```c
__libc_fatal ("Fatal error: glibc detected an invalid stdio handle\n");
```

**后果：** 如果 vtable 是非法的，程序会直接 **abort** 终止。

**影响：** 这一检查使得以往使用 vtable 进行利用的技术很难实现。攻击者无法再简单地伪造一个 vtable 指向任意地址来劫持控制流。

---

## 6. 利用思路转变：从 vtable 到 _IO_FILE 内部字段

在 vtable 难以被利用之后，利用的关注点从 **vtable** 转移到了 **`_IO_FILE` 结构内部的域**中。

### 背景知识

`_IO_FILE` 在使用标准 IO 库时会进行创建并负责维护一些相关信息。其中有一些域是表示调用诸如 `fwrite`、`fread` 等函数时**写入地址**或**读取地址**的。

### 核心思路

如果可以控制这些数据，就可以实现：
- **任意地址写**（Arbitrary Write）
- **任意地址读**（Arbitrary Read）

---

## 7. 任意地址读与任意地址写

### 任意地址读

任意地址读在前面的课程中已经讲过，就是利用 **stdout** 来实现的。通过控制 stdout 对应的 `_IO_FILE` 结构体中的缓冲区指针，可以在调用 `printf`/`puts` 等输出函数时从任意地址读取数据。

### 任意地址写

本课程重点讲解利用 **stdin** 来进行任意地址写。通过控制 stdin 对应的 `_IO_FILE` 结构体中的缓冲区指针，可以在调用 `scanf`/`gets` 等输入函数时向任意地址写入数据。

---

## 8. _IO_FILE 结构体关键字段

```c
char* _IO_read_ptr;    /* Current read pointer */
char* _IO_read_end;    /* End of get area. */
char* _IO_read_base;   /* Start of putback+get area. */
char* _IO_write_base;  /* Start of put area. */
char* _IO_write_ptr;   /* Current put pointer. */
char* _IO_write_end;   /* End of put area. */
char* _IO_buf_base;    /* Start of reserve area. */
char* _IO_buf_end;     /* End of reserve area. */
/* The following fields are used to support backing up and undo. */
char *_IO_save_base;   /* Pointer to start of non-current get area. */
char *_IO_backup_base; /* Pointer to first valid character of backup area */
char *_IO_save_end;    /* Pointer to end of non-current get area. */
```

### 关键字段说明

| 字段 | 含义 | 利用价值 |
|------|------|----------|
| `_IO_buf_base` | 缓冲区的起始地址 | 控制读写操作的起始位置 |
| `_IO_buf_end` | 缓冲区的结束地址 | 控制读写操作的结束位置 |

通过控制 `_IO_buf_base` 和 `_IO_buf_end` 这两个数据，可以实现控制读写的操作，从而实现任意地址读/写。

### 利用优势

因为进程中包含了系统默认的**三个文件流** `stdin`、`stdout`、`stderr`，因此这种方式可以**不需要进程中存在文件操作**，通过 `scanf`/`printf` 一样可以进行利用。

---

## 9. vtable 的多种类型

vtable 在内存中实际有许多种：

| vtable 类型 | 说明 |
|-------------|------|
| `IO_file_jumps` | `_IO_FILE` 默认对应的虚函数表 |
| `IO_helper_jumps` | 辅助文件流使用的虚函数表 |
| `IO_str_jumps` | 字符串流（`_IO_strfile`）使用的虚函数表 |

不同 vtable 对应不同的虚函数实现，攻击者可以根据需要选择合适的 vtable 类型进行利用。

## 10. 利用 stdin 实现任意地址写

### 基本原理

利用 stdin 进行任意地址写的核心在于控制 `_IO_FILE` 结构体中的缓冲区相关字段，使得 `scanf`/`gets` 等输入函数将数据写入到攻击者指定的地址。

### 关键控制点

1. **`_IO_buf_base`** — 设置为目标写入地址
2. **`_IO_buf_end`** — 设置为目标写入地址 + 写入长度
3. **`_IO_read_ptr`** / **`_IO_read_end`** — 控制读取缓冲区状态

---

## 11. _IO_str_finish 利用技术

### 利用步骤

通过 `_IO_str_finish` 实现 getshell 需要完成以下步骤：

1. **设置 `_IO_USER_BUF = 0`** → 对应 flag 值为 `0xfbad2084`
2. **设置 `fp->_IO_buf_base = str_sh`** — 将缓冲区基址指向 `"/bin/sh"` 字符串
3. **设置 `fp + 0xe8 = system_addr`** — 将 vtable 中 finish 函数的位置覆盖为 `system` 地址
4. **调整 vtable**，使 `finish` 在对应位置，这里最好使用 `_IO_flush_all_lockp` 来进行触发

### _IO_str_finish 源码

```c
void
_IO_str_finish (_IO_FILE *fp, int dummy)
{
    if (fp->_IO_buf_base && !(fp->_flags & _IO_USER_BUF))
        ((_IO_strfile *) fp)->_s._free_buffer (fp->_IO_buf_base);
    fp->_IO_buf_base = NULL;

    _IO_default_finish (fp, 0);
}
```

### 源码分析

`_IO_str_finish` 的执行流程：

1. **检查条件**：`fp->_IO_buf_base` 非空 **且** `fp->_flags` 中 `_IO_USER_BUF` 位为 0
2. **调用 free_buffer**：如果条件满足，调用 `_free_buffer(fp->_IO_buf_base)`
3. **置空缓冲区**：`fp->_IO_buf_base = NULL`
4. **调用默认 finish**：`_IO_default_finish(fp, 0)`

### 利用原理

当我们将 `_IO_buf_base` 指向 `"/bin/sh"`，并将 `_free_buffer`（位于 vtable 的 finish 位置，即 `fp + 0xe8`）覆盖为 `system` 地址时：

- `_free_buffer(fp->_IO_buf_base)` 实际上执行的是 `system("/bin/sh")`
- 从而获得 shell

### 触发方式

使用 `_IO_flush_all_lockp` 来触发所有文件流的 finish 操作。该函数会在程序异常退出（如 `exit()`）时被调用，遍历所有文件流并执行 finish 操作。

## 12. 后续版本中的其他利用方法

在更新的 libc 版本中，上述 `_IO_str_finish` 利用方式也被修复了。但仍然有许多其他的利用方法：

### House of Pig

一种结合 IO_FILE 和 tcache 的利用技术，通过构造特定的堆布局来实现任意地址写。

### House of Emma

另一种 IO_FILE 相关的利用技术，利用 `_IO_FILE` 结构体中的特定字段组合来实现攻击。

### 新版本中 vtable 变得可写

在更新的 glibc 版本中，`_IO_vtables` 段的保护策略发生变化，vtable 变得可写，这为攻击者提供了新的利用可能性。

## 总结

### 知识脉络

```
glibc 2.23 及以前
  └── vtable 无检查 → 可直接伪造 vtable 劫持控制流

glibc 2.24
  └── 引入 vtable 检查机制
      ├── IO_validate_vtable: 检查 vtable 是否在 _IO_vtables 段内
      └── 检查失败 → __libc_fatal → abort

glibc 2.27+
  └── _IO_JUMPS_FUNC 加入 IO_validate_vtable 调用
  └── _vtable_offset 硬编码为 0

利用思路转变
  └── 从 vtable 劫持 → _IO_FILE 内部字段控制
      ├── 任意地址读（利用 stdout）
      ├── 任意地址写（利用 stdin）
      └── _IO_str_finish 利用（system("/bin/sh")）

更新版本
  └── _IO_str_finish 方式被修复
  └── 新方法：House of Pig、House of Emma、vtable 可写
```

### 关键要点

1. **vtable 检查机制**是 glibc 2.24 引入的重要安全加固，通过验证 vtable 指针是否在合法的 `_IO_vtables` 段内来防止伪造 vtable 攻击。

2. **利用焦点转移**：vtable 难以劫持后，攻击者转向控制 `_IO_FILE` 结构体内部字段（如 `_IO_buf_base`、`_IO_buf_end`）来实现任意地址读/写。

3. **stdin/stdout/stderr** 是进程中默认存在的三个文件流，利用它们不需要程序本身存在文件操作，通过 `scanf`/`printf` 即可触发。

4. **`_IO_str_finish` 利用**是一种经典的 getshell 技术，通过构造 `_IO_strfile` 结构体，将 `_free_buffer` 替换为 `system`，`_IO_buf_base` 指向 `"/bin/sh"`，最终实现 `system("/bin/sh")`。

5. **安全是持续对抗的过程**：每种利用方法都会在后续版本中被修复，但新的利用方法也会不断出现（House of Pig、House of Emma 等）。
