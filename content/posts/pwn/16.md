## 一、堆漏洞利用流程

### 1.1 核心思路

对于堆相关的漏洞，**无法直接做到对程序控制流的劫持**。想要劫持控制流，通常有以下两种途径：

#### 途径一：修改堆上的函数指针

利用程序本身对堆的使用方式，想办法修改堆上的函数指针，在程序调用堆上的数据时达成劫持控制流的目的。

```
堆漏洞 → 修改堆上函数指针 → 程序调用该指针 → 控制流劫持
```

#### 途径二：任意地址写 + libc hook

基于对堆分配机制的理解，达到**任意地址分配**，从而实现**任意地址写**。再由任意地址写 libc 当中的一些 hook 来达到劫持程序控制流的目标。

```
堆漏洞 → 任意地址分配 → 任意地址写 → 覆写 libc hook → 控制流劫持
```

### 1.2 常用 Hook：malloc_hook 与 free_hook

堆利用中常用的 hook 就是 `malloc_hook` 与 `free_hook`。

#### malloc_hook

```c
void *
__libc_malloc (size_t bytes)
{
    mstate ar_ptr;
    void *victim;

    _Static_assert (PTRDIFF_MAX <= SIZE_MAX / 2,
                    "PTRDIFF_MAX is not more than half of SIZE_MAX");

    void *(*hook) (size_t, const void *)
        = atomic_forced_read (__malloc_hook);
    if (__builtin_expect (hook != NULL, 0))
        return (*hook)(bytes, RETURN_ADDRESS (0));
    // ... 后续正常分配逻辑
}
```

**原理**：在 `__libc_malloc` 函数开头，会检查 `__malloc_hook` 是否为 NULL。如果不为 NULL，则直接调用 hook 指向的函数，传入 `bytes` 和返回地址作为参数，然后立即返回。这意味着如果我们能将 `__malloc_hook` 覆写为 `system` 或 `one_gadget` 的地址，下次调用 `malloc` 时就会执行我们的代码。

#### free_hook

```c
void
__libc_free (void *mem)
{
    mstate ar_ptr;
    mchunkptr p;          /* chunk corresponding to mem */

    void (*hook) (void *, const void *)
        = atomic_forced_read (__free_hook);
    if (__builtin_expect (hook != NULL, 0))
    {
        (*hook)(mem, RETURN_ADDRESS (0));
        return;
    }
    // ... 后续正常释放逻辑
}
```

**原理**：在 `__libc_free` 函数开头，会检查 `__free_hook` 是否为 NULL。如果不为 NULL，则直接调用 hook 指向的函数，传入被释放的指针 `mem` 和返回地址作为参数，然后立即返回。如果我们能将 `__free_hook` 覆写为 `system` 的地址，然后释放一个内容为 `"/bin/sh\x00"` 的 chunk，就能获得 shell。

> **注意**：在 glibc 2.34 及之后版本中，`malloc_hook` 和 `free_hook` 已被移除，需要采用其他利用手段（如 tcache poisoning、IO_FILE 利用等）。

### 1.3 利用流程总结

```
┌─────────────────────────────────────────────────────┐
│                  堆漏洞利用流程                        │
├─────────────────────────────────────────────────────┤
│  1. 发现堆漏洞（UAF / Off-by-One / Off-by-Null 等）    │
│         ↓                                           │
│  2. 利用漏洞构造堆布局（overlap / unlink / tcache等）   │
│         ↓                                           │
│  3. 实现任意地址读写能力                               │
│         ↓                                           │
│  4. 泄漏 libc 地址（通过 unsorted bin / IO_FILE 等）   │
│         ↓                                           │
│  5. 计算目标函数地址（system / one_gadget 等）          │
│         ↓                                           │
│  6. 覆写 hook（malloc_hook / free_hook）              │
│         ↓                                           │
│  7. 触发 hook，劫持控制流，获取 shell                  │
└─────────────────────────────────────────────────────┘
```

## 二、常见漏洞类型

### 2.1 Use-After-Free (UAF)

#### 2.1.1 定义

**Use After Free** 就是其字面所表达的意思——当一个内存块被释放之后再次被使用。

#### 2.1.2 三种场景分析

| 场景 | 描述 | 结果 |
|------|------|------|
| **场景 1** | 内存块被释放后，其对应的指针被设置为 NULL，然后再次使用 | 程序会崩溃（空指针解引用） |
| **场景 2** | 内存块被释放后，其对应的指针**没有**被设置为 NULL，然后在它下一次被使用之前，**没有代码**对这块内存块进行修改 | 程序很有可能可以正常运转 |
| **场景 3** | 内存块被释放后，其对应的指针**没有**被设置为 NULL，但是在它下一次使用之前，**有代码**对这块内存进行了修改 | 当程序再次使用这块内存时，就很有可能会出现奇怪的问题 |

> 在 CTF 题目中所利用的 UAF 多为**后面两种**场景。

#### 2.1.3 关键概念：悬挂指针（Dangling Pointer）

一般称被释放后**没有被设置为 NULL** 的内存指针为**悬挂指针**。

#### 2.1.4 常见利用方法

1. **存在 show 功能时**：可以考虑使用 **unsorted bin 配合 UAF** 输出 `main_arena` 的地址，用于计算 libc 基址。

   ```
   free(chunk) → chunk 进入 unsorted bin → fd/bk 指向 main_arena → UAF 读取 fd → 泄漏 libc 地址
   ```

2. **存在 edit 功能时**：可以考虑使用大部分攻击手法（如 tcache poisoning、fastbin attack、unlink 等）。

3. **无 edit 功能时**：考虑 **double free** 来构造攻击链。

#### 2.1.5 利用示例思路

```python
# 伪代码示例：UAF 泄漏 libc 地址
add(0x80, 'A' * 0x80)   # 申请一个大于 fastbin 大小的 chunk
free(0)                  # 释放后进入 unsorted bin
# 此时 chunk 的 fd 和 bk 指针指向 main_arena
show(0)                  # UAF：通过悬挂指针读取 fd 指针
# 从输出中提取 main_arena 地址，计算 libc 基址
libc_base = leaked_addr - 0x3ebca0  # 偏移根据具体 libc 版本确定
```

### 2.2 Off-by-One

#### 2.2.1 定义

严格来说，**off-by-one** 漏洞是一种特殊的溢出漏洞。off-by-one 指程序向缓冲区中写入时，写入的字节数超过了这个缓冲区本身所申请的字节数并且**只越界了一个字节**。

#### 2.2.2 为什么 off-by-one 在堆上可利用？

一般来说，单字节溢出被认为是难以利用的。但是因为 Linux 的堆管理机制 **ptmalloc** 验证的松散性，基于 Linux 堆的 off-by-one 漏洞利用起来并不复杂，并且**威力强大**。

> 需要说明的一点是，off-by-one 可以基于各种缓冲区的，比如栈、bss 段等等，但是堆上（heap based）的 off-by-one 是 CTF 中比较常见的。这里仅讨论堆上的 off-by-one 情况。

#### 2.2.3 利用原理

由于堆的分配机制，**free chunk 的 prev_size 是可以用作上一 chunk 的数据域的**。所以如果我们申请一个 `0x58` 的堆块，那么我们写 `0x59` 个字节就可以覆盖到下一 chunk 的最后 1 byte size。

```
┌──────────────────────┬──────────────────────┬──────────────────────┐
│  Chunk A (0x58)      │  Chunk B             │  Chunk C             │
│  [data: 0x58 bytes]  │  [prev_size][size]   │  [prev_size][size]   │
│                      │                      │                      │
│  写入 0x59 字节 ──────────────────────────────────→ 覆盖 Chunk B 的  │
│                      │                      │  size 的最低 1 byte   │
└──────────────────────┴──────────────────────┴──────────────────────┘
```

通过修改下一个 chunk 的 size 字段的最低字节，可以：
- 扩大下一个 chunk 的 size（如果最低字节从较小值变为较大值）
- 清除 size 字段的 `PREV_INUSE` 位（最低 bit），使堆管理器误认为前一个 chunk 是空闲的

#### 2.2.4 常见利用方法

| 场景 | 利用手法 |
|------|----------|
| **未开启 PIE** | 可以考虑 **unlink** 攻击 |
| **使用 fastbin** | 可以考虑 **Chunk Extend** 构造 **overlap** |

**Chunk Extend 构造 overlap 思路**：

```
1. 通过 off-by-one 修改下一个 chunk 的 size，使其变大
2. 释放被扩大的 chunk（它会覆盖后面 chunk 的区域）
3. 重新申请同样大小的 chunk，获得 overlap 区域的控制权
4. 利用 overlap 实现任意读写或泄漏
```

### 2.3 Off-by-Null (NULL Byte Off-by-One)

#### 2.3.1 定义

**off-by-null** 是 off-by-one 的一种特殊情况，即多写入的那个字节恰好是 `\x00`（NULL 字节）。

#### 2.3.2 利用特点

off-by-null 的利用是比较**苛刻**的，一般仅能选择使用**利用 small bin 的合并进行 overlap**。

#### 2.3.3 利用原理

当多写入的 NULL 字节覆盖了下一个 chunk 的 size 字段的最低字节时：

1. 如果原 size 的最低字节不为 0，覆盖为 0 后 size 会**变小**（例如 `0x91` → `0x90`）
2. 同时会清除 `PREV_INUSE` 位
3. 当释放后面的 chunk 时，堆管理器会尝试向前合并（consolidate backward）
4. 利用合并过程中的 unlink 操作，可以构造 overlap

```
利用流程：
1. 布局多个 chunk，使目标 chunk 后面紧跟一个 small bin 大小的 chunk
2. 通过 off-by-null 修改下一个 chunk 的 size（清除 PREV_INUSE 位）
3. 释放更后面的 chunk，触发向前合并
4. 合并过程中 unlink 被扩大的 chunk，产生 overlap
5. 利用 overlap 进行后续攻击
```

> **注意**：off-by-null 的利用条件比 off-by-one 更为严格，需要精心构造堆布局才能成功。

## 三、堆上的泄漏

### 3.1 常见泄漏方法

在堆利用中，获取 libc 地址是至关重要的一步。常见的泄漏方法包括：

| 泄漏方法 | 说明 |
|----------|------|
| **Unsorted Bin** | 利用 unsorted bin 中 chunk 的 fd/bk 指针泄漏 `main_arena` 地址 |
| **Small Bin** | 类似 unsorted bin，small bin 中的 chunk 也存有 libc 地址 |
| **Large Bin** | large bin 中的 chunk 同样存有 libc 地址 |
| **IO_FILE** | 利用 IO_FILE 结构体中的指针泄漏 libc 地址 |

### 3.2 Unsorted Bin 泄漏原理

#### 3.2.1 核心机制

Unsorted bin 的**头块与尾块**中会存放 libc 地址。构造多块时，还会存在 heap 地址，可以用来泄漏。

```
unsorted bin 链表结构：

main_arena + 0x60 (unsorted bin head)
    ↕ fd/bk
chunk1 (fd → main_arena+0x60, bk → chunk2)
    ↕
chunk2 (fd → chunk1, bk → main_arena+0x60)
```

- 每个 unsorted bin 中的 chunk 的 `fd` 和 `bk` 指针都指向链表中的相邻 chunk 或 `main_arena`
- `main_arena` 位于 libc 中，因此通过读取 unsorted bin chunk 的 fd/bk 指针可以泄漏 libc 地址

#### 3.2.2 GDB 调试示例

```
pwndbg> telescope 0x602000
00:0000│  r8  0x602000 — 0x0
01:0008│      0x602008 ◂— 0x111
02:0010│      0x602010 ◂— 0x7ffff7dd1b78 (main_arena+88) → 0x602760 — 0x0
03:0018│      0x602018 ◂— 0x602140 ◂— 0x0
04:0020│      0x602020 ◂— 0x0
...

pwndbg> telescope 0x602510
00:0000│      0x602510 ◂— 0x0
01:0008│      0x602518 ◂— 0x221
02:0010│      0x602520 ◂— 0x6022d0 ◂— 0x0
03:0018│      0x602528 ◂— 0x7ffff7dd1b78 (main_arena+88) → 0x602760 ◂— 0x0
04:0020│      0x602530 ◂— 0x0
```

从上面的调试输出可以看到：
- `0x602010` 处存储了 `0x7ffff7dd1b78 (main_arena+88)`，这就是 libc 中的地址
- `0x602528` 处同样存储了 `main_arena+88` 的地址
- 这些地址就是 unsorted bin 中 chunk 的 fd/bk 指针

#### 3.2.3 泄漏步骤

```python
# 伪代码示例：通过 unsorted bin 泄漏 libc 地址

# 1. 申请一个大于 fastbin 大小（>0x80）且小于 small bin 最大大小的 chunk
add(0x90, 'A' * 0x90)

# 2. 释放该 chunk，使其进入 unsorted bin
free(0)

# 3. 通过 UAF 或 show 功能读取 chunk 的 fd 指针
show(0)

# 4. 从输出中提取 main_arena 地址
leaked_addr = u64(output[:6].ljust(8, b'\x00'))

# 5. 根据 libc 版本计算 libc 基址
# main_arena 偏移因 libc 版本而异，常见偏移：
#   glibc 2.23: main_arena + 88 = libc_base + 0x3c4b78
#   glibc 2.27: main_arena + 96 = libc_base + 0x3ebc40
#   glibc 2.31: main_arena + 96 = libc_base + 0x1ebbe0
libc_base = leaked_addr - 0x3c4b78  # 以 glibc 2.23 为例

# 6. 计算目标函数地址
system_addr = libc_base + libc.sym['system']
free_hook = libc_base + libc.sym['__free_hook']
```

#### 3.2.4 各 bin 中存储 libc 地址的情况总结

| Bin 类型 | 是否存储 libc 地址 | 说明 |
|----------|-------------------|------|
| **Fast Bin** | 否 | 只存储 heap 地址（指向下一个 fastbin chunk） |
| **Unsorted Bin** | 是 | fd/bk 指向 `main_arena`，可泄漏 libc 地址 |
| **Small Bin** | 是 | fd/bk 指向 `main_arena` 或相邻 chunk |
| **Large Bin** | 是 | 包含 `fd_nextsize`/`bk_nextsize`，也存有 libc 地址 |

> **关键结论**：这些 bins 都会存有 libc 地址，可以尝试用来泄漏。在 CTF 中，**unsorted bin 泄漏**是最常用、最基础的 libc 地址泄漏方法。

## 附录：关键知识点速查

### A. 堆 Chunk 结构

```
┌──────────────────────────────────────────────┐
│              Chunk Header                     │
├──────────────────┬───────────────────────────┤
│  prev_size (8B)  │  size (8B)                │
│  (前一个chunk大小) │  (当前chunk大小+标志位)     │
├──────────────────┴───────────────────────────┤
│              User Data                        │
│  (用户数据区域)                                │
├───────────────────────────────────────────────┤
│  fd (8B)  │  bk (8B)  │  ... (仅 free chunk)  │
│  (前向指针)  │  (后向指针)  │                    │
└───────────────────────────────────────────────┘
```

**size 字段的标志位**：
- **Bit 0 (PREV_INUSE)**：前一个 chunk 是否在使用中
- **Bit 1 (IS_MMAPPED)**：chunk 是否通过 mmap 分配
- **Bit 2 (NON_MAIN_ARENA)**：chunk 是否属于非主 arena

### B. 常见 libc 偏移参考

| glibc 版本 | main_arena 偏移 | malloc_hook 偏移 | free_hook 偏移 |
|------------|----------------|-----------------|---------------|
| 2.23 | 0x3c4b20 | 0x3c4b10 | 0x3c67a8 |
| 2.27 | 0x3ebc40 | 0x3ebc30 | 0x3ed8e8 |
| 2.31 | 0x1ebbe0 | 0x1ebc30 | 0x1ed8e8 |

> 以上偏移为 Ubuntu 默认 libc 的参考值，实际题目中需根据具体 libc 文件确定。

### C. 常用 pwntools 模板

```python
from pwn import *

context(os='linux', arch='amd64', log_level='debug')

# 加载程序与 libc
p = process('./pwn')
libc = ELF('./libc.so.6')

# 常用操作封装
def add(size, content):
    p.sendlineafter('choice:', '1')
    p.sendlineafter('size:', str(size))
    p.sendafter('content:', content)

def free(idx):
    p.sendlineafter('choice:', '2')
    p.sendlineafter('index:', str(idx))

def show(idx):
    p.sendlineafter('choice:', '3')
    p.sendlineafter('index:', str(idx))

def edit(idx, content):
    p.sendlineafter('choice:', '4')
    p.sendlineafter('index:', str(idx))
    p.sendafter('content:', content)

# 泄漏 libc
add(0x90, 'A' * 0x90)  # idx 0
free(0)
show(0)
libc_addr = u64(p.recv(6).ljust(8, b'\x00'))
libc_base = libc_addr - 0x3c4b78  # 根据实际偏移调整
log.success(f'libc base: {hex(libc_base)}')

# 覆写 free_hook
system_addr = libc_base + libc.sym['system']
free_hook = libc_base + libc.sym['__free_hook']

add(0x80, '/bin/sh\x00')  # idx 1，存放 /bin/sh
# ... 利用漏洞将 free_hook 覆写为 system_addr ...
free(1)  # 触发 system("/bin/sh")

p.interactive()
```

## 学习建议

1. **先理解堆的基本结构**：掌握 chunk 结构、bin 分类（fastbin/unsorted/small/large/tcache）、分配与释放流程。
2. **从 UAF 入手**：UAF 是最基础也最常见的堆漏洞，理解其原理后再学习其他漏洞类型。
3. **动手实践**：每学一种漏洞类型，找对应的 CTF 题目进行练习，使用 GDB + pwntools 调试验证。
4. **关注 glibc 版本差异**：不同版本的 glibc 在堆管理机制上有显著差异（如 tcache 的引入、hook 的移除等）。
5. **建立漏洞利用思维链**：漏洞发现 → 堆布局构造 → 地址泄漏 → 任意写 → 控制流劫持。
