## 一、printf 内部机制分析

### 1.1 `__register_printf_function`

在 glibc 中存在一个函数 `__register_printf_function`，其作用是为格式化字符为 `spec` 的格式化输出注册自定义处理函数。其本质是对 `__register_printf_specifier` 函数的封装。

函数原型如下：

```c
int
__register_printf_specifier (int spec, printf_function converter,
                             printf_arginfo_size_function arginfo)
{
    if (spec < 0 || spec > (int) UCHAR_MAX)
    {
        __set_errno (EINVAL);
        return -1;
    }

    int result = 0;
    __libc_lock_lock (lock);

    if (__printf_function_table == NULL)
    {
        __printf_arginfo_table = (printf_arginfo_size_function **)
            calloc (UCHAR_MAX + 1, sizeof (void *) * 2);
        if (__printf_arginfo_table == NULL)
        {
            result = -1;
            goto out;
        }

        __printf_function_table = (printf_function **)
            (__printf_arginfo_table + UCHAR_MAX + 1);
    }
    // ... 后续注册逻辑
}
```

**关键变量：**

| 变量名 | 说明 |
|--------|------|
| `__printf_function_table` | 存储每个格式化字符对应的处理函数指针的数组 |
| `__printf_arginfo_table` | 存储每个格式化字符对应的参数信息函数的数组 |

这两个变量在 `__register_printf_function` 被调用时才会被初始化（懒初始化）。正常情况下它们为 `NULL`，即走默认的 printf 处理流程。

### 1.2 `vfprintf` —— printf 的最终调用函数

printf 的最终调用函数是 `vfprintf`，其源码位于：

```
stdio-common/vfprintf-internal.c
```

`vfprintf` 函数签名：

```c
vfprintf (FILE *s, const CHAR_T *format, va_list ap, unsigned int mode_flags)
{
    /* The character used as thousands separator.  */
    THOUSANDS_SEP_T thousands_sep = 0;
    /* The string describing the size of groups of digits.  */
    const char *grouping;
    /* Place to accumulate the result.  */
    int done;
    /* Current character in format string.  */
    const UCHAR_T *f;
    /* End of leading constant string.  */
    const UCHAR_T *lead_str_end;
    /* Points to next format specifier.  */
    const UCHAR_T *end_of_spec;
    /* Buffer intermediate results.  */
    CHAR_T work_buffer[WORK_BUFFER_SIZE];
    CHAR_T *workstart = NULL;
    CHAR_T *workend;
    /* We have to save the original argument pointer.  */
    va_list ap_save;
    /* Count number of specifiers we already processed.  */
    int nspecs_done;
    /* For the %m format we may need the current 'errno' value.  */
    int save_errno = errno;
    /* 1 if format is in read-only memory, -1 if it is in writable memory,
       0 if unknown.  */
    int readonly_format = 0;
    /* Orient the stream.  */
    #ifdef ORIENT
        ORIENT;
    #endif
    /* Sanity check of arguments.  */
    ARGCHECK (s, format);
    // ...
}
```

`vfprintf` 是 printf 系列函数的核心实现，负责解析格式字符串、提取参数、格式化输出。

### 1.3 自定义 handler 注册机制

在 `vfprintf` 源码的第 1337 行可以发现，printf 的格式化字符串是可以自行注册 handler 的：

```c
/* Use the slow path in case any printf handler is registered.  */
if (__glibc_unlikely (__printf_function_table != NULL
                      || __printf_modifier_table != NULL
                      || __printf_va_arg_table != NULL))
    goto do_positional;
```

**关键逻辑：**

- 只要 `__printf_function_table`、`__printf_modifier_table`、`__printf_va_arg_table` 这三个变量中**任意一个不为 NULL**，就会直接跳转到 `do_positional` 标签进行处理，而**不是走正常的处理流程**。
- 这意味着如果攻击者能够控制这些变量的值，就可以劫持 printf 的执行流。

---

### 1.4 `printf_positional` 与 `__parse_one_specmb`

跳转到 `do_positional` 后，会调用 `printf_positional` 函数：

```c
do_positional:
    if (__glibc_unlikely (workstart != NULL))
    {
        free (workstart);
        workstart = NULL;
    }
    done = printf_positional (s, format, readonly_format, ap, &ap_save,
                              done, nspecs_done, lead_str_end, work_buffer,
                              save_errno, grouping, thousands_sep, mode_flags);
```

经过对源码的分析理解，得到以下逻辑：

#### 步骤 1：`__parse_one_specmb` 解析格式字符串

`printf_positional` 函数中经过 `__parse_one_specmb` 函数对格式化字符串进行解析，返回值是取了几个参数：

```c
/* Parse the format specifier.  */
#ifdef COMPILE_NPRINTF
    nargs += __parse_one_specwc (f, nargs, &specs[nspecs], &max_ref_arg);
#else
    nargs += __parse_one_specmb (f, nargs, &specs[nspecs], &max_ref_arg);
#endif
```

#### 步骤 2：`__printf_function_table` 不为空时调用 `__printf_arginfo_table`

在 `__parse_one_specmb` 中，当 `__printf_function_table` 不为空时，会调用 `__printf_arginfo_table` 中的函数来进行解析：

```c
if (__builtin_expect (__printf_function_table == NULL, 1)
    || spec->info.spec > UCHAR_MAX
    || __printf_arginfo_table[spec->info.spec] == NULL)
    /* We don't try to get the types for all arguments if the format
       uses more than one.  The normal case is covered though.  If
       the call returns -1 we continue with the normal specifiers.  */
    || (int) (spec->ndate_args = (*__printf_arginfo_table[spec->info.spec])
              (&spec->info, 1, &spec->data_arg_type, &spec->size)) < 0)
{
    // 正常处理流程
}
```

#### 步骤 3：调用对应函数进行输出

在 `printf_positional` 中，最终会调用 `__printf_function_table` 中注册的函数进行实际输出。

---

### 1.5 关键逻辑总结

整个 printf 自定义 handler 的调用链如下：

```
printf()
  └── vfprintf()
        ├── 检查 __printf_function_table 等变量是否非空
        │     └── 非空 → goto do_positional
        └── printf_positional()
              ── __parse_one_specmb()
                    ├── 解析格式字符串
                    └── 若 __printf_function_table 非空
                          ├── 调用 __printf_arginfo_table[spec] 获取参数信息
                          └── 调用 __printf_function_table[spec] 执行输出
```

**攻击面分析：**

如果攻击者能够通过漏洞（如堆溢出、任意地址写等）修改以下两个全局变量的值：

1. **`__printf_function_table`** —— 设置为非空值
2. **`__printf_arginfo_table`** —— 设置为攻击者可控的内存地址

然后在可控内存中布置 gadget 地址，再触发 printf 的格式化字符串处理，即可劫持控制流。

## 二、House of Husk

### 2.1 技术概述

House of Husk 是一种基于 printf 内部机制的**新型堆利用技术**。通过前面的源码分析，我们可以得出一种新的利用方式：利用 glibc 中 printf 的自定义 handler 注册机制，通过修改关键全局变量来劫持程序控制流。

### 2.2 利用步骤

House of Husk 的利用分为以下四个步骤：

#### 步骤 1：将 `__printf_function_table` 的值设置为非空

```
目标：使 vfprintf 中的检查条件成立，跳转到 do_positional 分支
方法：通过任意地址写漏洞，将 __printf_function_table 覆盖为非零值
```

#### 步骤 2：将 `__printf_arginfo_table` 的值设置为一个可控的内存地址

```
目标：使 __printf_arginfo_table[spec] 指向攻击者可控的内存区域
方法：通过任意地址写漏洞，将 __printf_arginfo_table 覆盖为可控地址
```

#### 步骤 3：在内存地址中布置 gadget 地址

```
目标：在 __printf_arginfo_table 指向的内存区域中布置 ROP gadget 或 shellcode 地址
方法：在可控内存（如堆上）提前布局好所需的函数指针/gadget
```

#### 步骤 4：触发 printf 中的格式化字符串

```
目标：执行被劫持的控制流
方法：调用 printf 并传入包含特定格式化字符的字符串，触发 __printf_function_table 中的函数调用
```

### 2.3 适用场景

House of Husk 技术可以获得一种针对**任意地址写**的利用方法。

**一般适用场景：**

- **Unsorted Bin Attack** —— 通过 unsorted bin 攻击实现任意地址写
- **Large Bin Attack** —— 通过 large bin 攻击实现任意地址写

**前提条件：**

| 条件 | 说明 |
|------|------|
| 任意地址写原语 | 需要能够向指定地址写入数据 |
| 可控内存区域 | 需要有一块可读写且内容可控的内存（通常为堆） |
| printf 调用 | 程序中需要存在 printf 调用且格式化字符串部分可控 |
| 无 PIE 或已泄露 libc 基址 | 需要知道 `__printf_function_table` 和 `__printf_arginfo_table` 的地址 |

## 三、Relative Overwrite

### 3.1 技术概述

Relative Overwrite 是一种新的利用手法，其核心思想是通过覆盖 `global_max_fast` 来扩大 fastbin 的范围，进而利用释放一个大 chunk 时造成的数组越界来实现堆地址的越界写。

### 3.2 原理分析

#### `global_max_fast` 与 fastbin 的关系

```
fastbinsY 数组位于 main_arena 当中，也就是在 libc 中。
当 free 一个 chunk 的时候，会向 fastbinsY 数组中写入地址。
```

**关键结构：**

```
main_arena
├── ...
├── fastbinsY[0]   ← 大小为 0x20 的 fastbin
├── fastbinsY[1]   ← 大小为 0x30 的 fastbin
├── fastbinsY[2]   ← 大小为 0x40 的 fastbin
├── ...
├── fastbinsY[N]   ← 大小为 (N+1)*0x10+0x10 的 fastbin
└── ...
```

`global_max_fast` 决定了 fastbin 的最大大小。默认情况下，只有小于等于 `global_max_fast` 的 chunk 才会被放入 fastbin。

#### 扩大 fastbin 范围

如果修改了 `global_max_fast`，扩大 fastbin 范围，在释放一个大 chunk 的时候，就会造成**数组越界**。

```
正常情况：
  global_max_fast = 0x80
  free(chunk_of_size_0x90) → 不进入 fastbin，进入 unsorted bin

修改后：
  global_max_fast = 0x200（被恶意扩大）
  free(chunk_of_size_0x190) → 计算 fastbin 索引 = (0x190 - 0x10) / 0x10 = 0x18
  → fastbinsY[0x18] 越界写入！
```

### 3.3 利用思路

**Relative Overwrite 的核心思路：**

```
1. 通过漏洞覆盖 global_max_fast，将其值扩大
2. 释放一个大 chunk，使其被当作 fastbin chunk 处理
3. 由于 fastbin 索引计算超出 fastbinsY 数组范围，造成越界写
4. 利用越界写修改关键数据结构（如 __printf_function_table、__printf_arginfo_table 等）
5. 触发 printf 调用，劫持控制流
```

**与 House of Husk 的结合：**

Relative Overwrite 可以作为 House of Husk 的前置步骤，通过越界写来实现对 `__printf_function_table` 和 `__printf_arginfo_table` 的修改，从而完成完整的利用链。
