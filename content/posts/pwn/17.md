## 二、Unlink 介绍

### 2.1 什么是 Unlink

**Unlink** 是 glibc 堆管理器（ptmalloc）中的一个核心操作，用来将一个**双向链表**（只存储空闲的 chunk）中的一个元素取出来。

简单来说，当一个空闲 chunk 需要被从 bin 链表中移除时（例如被分配出去、或与相邻 chunk 合并），unlink 操作负责将该 chunk 从链表中"摘除"，并维护链表的前后指针关系。

### 2.2 Unlink 的使用场景

Unlink 可能在以下函数/场景中被调用：

#### （1）`malloc`

- 从**恰好大小合适**的 **large bin** 中获取 chunk 时，会调用 unlink 将目标 chunk 从 large bin 链表中取出。

#### （2）`free`

- **后向合并**：合并物理相邻的**低地址**空闲 chunk 时，需要将被合并的 chunk 从 bin 中 unlink。
- **前向合并**：合并物理相邻的**高地址**空闲 chunk（除了 top chunk）时，同样需要 unlink。

#### （3）`malloc_consolidate`

- **后向合并**：合并物理相邻的**低地址**空闲 chunk。
- **前向合并**：合并物理相邻的**高地址**空闲 chunk（除了 top chunk）。

#### （4）`realloc`

- **前向扩展**：合并物理相邻的**高地址**空闲 chunk（除了 top chunk）时，会触发 unlink。

### 2.3 为什么 Fastbin / Small Bin / Unsorted Bin 不使用 Unlink

| Bin 类型 | 是否使用 Unlink | 原因 |
|----------|----------------|------|
| **Fastbin** | 否 | 使用**单链表**结构（只有 fd 指针），不需要 unlink 的双向链表操作 |
| **Small Bin** | 否 | 采用**先进先出（FIFO）**策略，直接从头部/尾部取 chunk，不涉及复杂的链表摘除 |
| **Unsorted Bin** | 否 | 依次遍历处理 unsorted bin 时也没有使用 unlink，而是直接遍历 |
| **Large Bin** | **是** | 从比请求的 chunk 所在的 bin 大的 bin 中取 chunk 时使用 unlink |

> **关键理解**：这就是为什么堆漏洞经常出现在 fastbin 和 small bin 相关操作中的原因之一 —— 它们绕过了 unlink 的安全检查机制。

## 三、Unlink 的基本原理与过程

### 3.1 双向链表结构回顾

在 glibc 的堆管理中，large bin 使用**双向链表**来组织空闲 chunk。每个 chunk 包含以下关键字段：

```
+------------------+
|    prev_size     |  ← 前一个 chunk 的大小（如果前一个 chunk 空闲）
+------------------+
|      size        |  ← 当前 chunk 的大小及标志位
+------------------+
|       fd         |  ← 指向链表中前一个 chunk（forward）
+------------------+
|       bk         |  ← 指向链表中后一个 chunk（backward）
+------------------+
|  Unused bytes    |  ← 用户数据区域
+------------------+
```

在双向链表中：
- `fd`（forward）：指向链表中**前一个**节点
- `bk`（backward）：指向链表中**后一个**节点

链表的头节点（bin 本身）的 fd 指向链表中最大的 chunk，bk 指向最小的 chunk。

### 3.2 Unlink 的核心目的

Unlink 的目的是**把一个双向链表中的空闲 chunk 拿出来**，然后和目前物理相邻的 free chunk 进行合并操作。

基本过程如下：

```
原始链表：  BK <-> P <-> FD

unlink(P) 之后：
           BK <-> FD
```

即：
- `FD->bk = BK`（FD 的 bk 指针指向 BK）
- `BK->fd = FD`（BK 的 fd 指针指向 FD）

这样 P 就从链表中被移除了。

### 3.3 Unlink 的源码分析

以下是 glibc 中 unlink 宏的核心逻辑（简化版）：

```c
#define unlink(AV, P, BK, FD) {
    FD = P->fd;
    BK = P->bk;

    // ===== 安全检查（现代版本新增）=====
    // 检查 chunk size 与 prev_size 是否一致
    if (__builtin_expect (chunksize(P) != prev_size (next_chunk(P)), 0))
        malloc_printerr ("corrupted size vs. prev_size");

    // 检查双向链表一致性（FD->bk == P && BK->fd == P）
    if (__builtin_expect (FD->bk != P || BK->fd != P, 0))
        malloc_printerr (check_action, "corrupted double-linked list", P, AV);

    // 检查 next_size 相关的一致性
    if (__builtin_expect (P->fd_nextsize->bk_nextsize != P, 0)
        || __builtin_expect (P->bk_nextsize->fd_nextsize != P, 0))
        malloc_printerr (check_action,
            "corrupted double-linked list (not small)", P, AV);
    // ===== 安全检查结束 =====

    // 处理 nextsize 链表
    if (FD->fd_nextsize == NULL) {
        // 如果 FD 的 fd_nextsize 为 NULL，说明 P 是 nextsize 链表中唯一的节点
        // 直接将 BK 的 nextsize 指针指向 FD
        if (P->fd_nextsize != P) {
            FD->fd_nextsize = P->fd_nextsize;
            FD->bk_nextsize = P->bk_nextsize;
            P->fd_nextsize->bk_nextsize = FD;
            P->bk_nextsize->fd_nextsize = FD;
        }
    } else {
        // 如果 FD 的 fd_nextsize 不为 NULL
        // 将 P 的 nextsize 指针指向 FD 的 nextsize
        FD->fd_nextsize = P->fd_nextsize;
        FD->bk_nextsize = P->bk_nextsize;
        P->fd_nextsize->bk_nextsize = FD;
        P->bk_nextsize->fd_nextsize = FD;
    }

    // ===== 核心摘除操作 =====
    FD->bk = BK;
    BK->fd = FD;
}
```

**关键操作总结**：

| 操作 | 含义 |
|------|------|
| `FD = P->fd` | 获取 P 的前驱节点 |
| `BK = P->bk` | 获取 P 的后继节点 |
| `FD->bk = BK` | 前驱的后继指向 P 的后继 |
| `BK->fd = FD` | 后继的前驱指向 P 的前驱 |

## 四、早期 Unlink 漏洞利用（无检查时代）

### 4.1 早期 Unlink 的安全缺陷

在最初 unlink 实现的时候，**没有对双向链表进行一致性检查**，也就是说，没有以下代码：

```c
// 以下检查在早期版本中不存在！

// 检查1：chunk size 与 prev_size 一致性
if (__builtin_expect (chunksize(P) != prev_size (next_chunk(P)), 0))
    malloc_printerr ("corrupted size vs. prev_size");

// 检查2：双向链表一致性
if (__builtin_expect (FD->bk != P || BK->fd != P, 0))
    malloc_printerr (check_action, "corrupted double-linked list", P, AV);

// 检查3：next_size 相关一致性
if (__builtin_expect (P->fd_nextsize->bk_nextsize != P, 0)
    || __builtin_expect (P->bk_nextsize->fd_nextsize != P, 0))
    malloc_printerr (check_action,
        "corrupted double-linked list (not small)", P, AV);
```

### 4.2 攻击原理

如果通过某种方式（比如**堆溢出**）将 Nextchunk 的 `fd` 和 `bk` 指针修改为指定的值，则当我们 `free(Q)` 时，可以触发 unlink 并实现任意地址写。

**攻击场景图示**：

```
修改前：
  Q chunk:
    fd = target addr - 12
    bk = expect value

  Nextchunk of Q:
    fd = (原始值)
    bk = (原始值)

通过溢出修改后：
  Q chunk:
    fd = target addr - 12    ← 被修改
    bk = expect value         ← 被修改
```

### 4.3 任意地址写实现

假设我们构造了以下值：

```
FD = P->fd = target addr - 12
BK = P->bk = expect value
```

unlink 执行核心操作：

```
FD->bk = BK
即 *(target addr - 12 + 12) = BK = expect value
即 *(target addr) = expect value

BK->fd = FD
即 *(expect value + 8) = FD = target addr - 12
```

**效果**：
- `*(target addr) = expect value` → 在目标地址写入期望值
- `*(expect value + 8) = target addr - 12` → 在期望值地址 +8 处写入目标地址 -12

> 这样就可以达到**任意地址写**的目的。

## 五、现代 Unlink 的安全检查机制

### 5.1 新增的双向链表一致性检查

现代 glibc 在 unlink 中加入了严格的安全检查：

```c
// 核心检查条件
FD->bk == P  &&  BK->fd == P
```

即：
- `P->fd->bk` 必须等于 `P`（前驱的后继必须指回自己）
- `P->bk->fd` 必须等于 `P`（后继的前驱必须指回自己）

这确保了双向链表的完整性，防止被恶意篡改。

### 5.2 为什么旧攻击方法会失败

按照之前的攻击方法：

```
FD->bk = target addr - 12 + 12 = target_addr
BK->fd = expect value + 8
```

检查条件要求：
- `FD->bk == P` → `target_addr == P` ❌ （通常不成立）
- `BK->fd == P` → `expect value + 8 == P` ❌ （通常不成立）

**显然会失败！**

### 5.3 绕过思路

如果我们使得：
- `expect value + 8 == P`
- `target_addr == P`

那么就可以通过检查。

此时：
- `*P = expect value = P - 8`
- `*P = target addr - 12 = P - 12`

**即改写了指针 P 的内容，将其指向了比自己低 12 的地址处。**

虽然这不是任意地址写，但我们成功修改了 P 指针本身的内容，使其指向了一个我们可以控制的区域 —— 这就是**指针劫持**的基础。

## 六、现代 Unlink 利用技术（Fake Chunk 方法）

### 6.1 利用前提条件

要成功利用现代 unlink，需要满足以下条件：

1. **存在堆溢出漏洞**：能够溢出修改相邻 chunk 的元数据（`prev_size`、`prev_inuse` 位、`fd`、`bk` 等）
2. **目标指针位于堆上**：我们需要劫持的指针（如函数指针、GOT 表项的间接引用等）位于堆的某个 chunk 中
3. **能够触发 free 操作**：需要能够 free 被篡改的 chunk，从而触发 unlink

### 6.2 利用步骤详解

#### 步骤 1：构造 Fake Chunk，修改其 fd、bk

在目标指针 P 所在的 chunk 的数据区域中，构造一个**伪造的 chunk（fake chunk）**，并精心设置其 `fd` 和 `bk` 指针：

```
fake_chunk.fd = P - 12   （即 &P - 12，指向 P 的 fd 字段前 12 字节处）
fake_chunk.bk = P - 8    （即 &P - 8，指向 P 的 bk 字段前 8 字节处）
```

> 在 64 位系统中，偏移量可能不同（fd 偏移 16，bk 偏移 24），需要根据实际架构调整。

#### 步骤 2：通过溢出修改下一个 chunk 的 prev_size

通过堆溢出漏洞，修改下一个 chunk 的 `prev_size` 字段，使其指向我们构造的 fake_chunk：

```
next_chunk.prev_size = fake_chunk 到 next_chunk 的距离
```

#### 步骤 3：修改下一个 chunk 的 prev_inuse 位，触发 unlink

将下一个 chunk 的 `prev_inuse` 位清零（设为 0），这样当 free 下一个 chunk 时，glibc 会认为前一个 chunk 是空闲的，从而尝试将其从 bin 中 unlink。

### 6.3 内存布局图解

```
地址布局（从低到高）：

+------------------+  ← A（指针 P 的地址）
|    指针 P        |  ← 我们要劫持的指针
+------------------+
|    fake_prev     |  ← fake chunk 的 prev_size
+------------------+
|    fake_size     |  ← fake chunk 的 size
+------------------+
|    A - 12        |  ← fake chunk 的 fd = P - 12
+------------------+
|    A - 8         |  ← fake chunk 的 bk = P - 8
+------------------+
|    prev_size     |  ← 下一个 chunk 的 prev_size（被溢出修改为指向 fake_chunk）
+------------------+
|      size        |  ← 下一个 chunk 的 size（prev_inuse 位被清零）
+------------------+
|   User Data      |
+------------------+
```

### 6.4 校验通过的原理推导

当 free 触发 unlink 时，P 指向我们的 fake_chunk：

```
P = fake_chunk
FD = P->fd = A - 12
BK = P->bk = A - 8
```

**安全检查验证**：

```
FD->bk = *(A - 12 + 12) = *(A) = P  ✓
BK->fd = *(A - 8 + 8) = *(A) = P    ✓
```

**顺利通过校验！**

**unlink 执行后的效果**：

```
FD->bk = BK  →  *(A - 12 + 12) = A - 8  →  *A = A - 8
BK->fd = FD  →  *(A - 8 + 8) = A - 12   →  *A = A - 12
```

最终：`*A = A - 12`

即指针 P 的值被修改为 `A - 12`，指向了 fake_chunk 内部我们可控的区域。之后我们就可以通过这个被劫持的指针来**读写任意内容**。

## 七、Unlink 利用流程与实战应用

### 7.1 完整利用流程

```
┌─────────────────────────────────────────────────────┐
│  1. 分析程序，找到堆溢出漏洞和可被劫持的指针          │
─────────────────────────────────────────────────────┤
│  2. 在堆上构造 fake chunk，设置 fd/bk 指针           │
├─────────────────────────────────────────────────────┤
│  3. 通过溢出修改相邻 chunk 的 prev_size              │
├─────────────────────────────────────────────────────┤
│  4. 清除相邻 chunk 的 prev_inuse 位                  │
├─────────────────────────────────────────────────────┤
│  5. free 相邻 chunk，触发 unlink                     │
├─────────────────────────────────────────────────────┤
│  6. 指针 P 被劫持，指向 fake chunk 内部              │
├─────────────────────────────────────────────────────┤
│  7. 通过被劫持的指针实现任意读写                      │
├─────────────────────────────────────────────────────┤
│  8. 配合 edit 功能修改 GOT 表或劫持函数               │
├─────────────────────────────────────────────────────┤
│  9. 获取 shell / 完成利用                             │
└─────────────────────────────────────────────────────┘
```

### 7.2 配合 GOT 表修改

通常利用 unlink 可以达到 **heap base 上的任意写**，这时配合程序的 **edit 功能**就可以：

1. **修改 GOT 表**：将 GOT 表中的函数地址替换为 `system` 或其他有用函数的地址
2. **进行泄漏**：通过修改 GOT 表项为 `puts`/`printf` 等函数来泄漏 libc 地址
3. **函数劫持**：将关键函数（如 `free`、`atoi` 等）的 GOT 表项替换为 `system`，然后传入 `/bin/sh` 获取 shell

### 7.3 配合 Libc 替换（patchelf）

在 CTF 实战中，经常需要替换目标程序的 libc 版本以匹配本地环境。常用工具是 **patchelf**：

#### 查看当前链接的库

```bash
ldd note2
```

输出示例：
```
linux-vdso.so.1 (0x00007ffc3fc8a000)
libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f6e51152000)
/lib64/ld-linux-x86-64.so.2 (0x00007f6e5135a000)
```

#### 替换 libc 和 ld

```bash
# 设置新的 interpreter（ld）
patchelf --set-interpreter /path/to/ld-2.23.so ./note2

# 替换 libc
patchelf --replace-needed libc.so.6 /path/to/libc-2.23.so ./note2
```

#### 验证替换结果

```bash
ldd note2
```

确认输出中 libc 和 ld 的路径已指向目标版本。

> **注意**：patchelf 的 `--replace-needed` 参数需要指定原始的库名（如 `libc.so.6`），而不是路径。

## 八、总结与学习要点

### 核心知识点回顾

| 知识点 | 要点 |
|--------|------|
| **Unlink 定义** | 从双向链表中移除一个空闲 chunk 的操作 |
| **使用场景** | malloc（large bin）、free（合并）、malloc_consolidate、realloc |
| **早期漏洞** | 无安全检查，可通过溢出 fd/bk 实现任意地址写 |
| **现代检查** | `FD->bk == P && BK->fd == P` 双向链表一致性检查 |
| **绕过方法** | 构造 fake chunk，使 fd/bk 指向指针 P 自身附近，通过校验后劫持指针 |
| **利用效果** | 将堆上指针修改为指向可控区域，配合 edit 实现 GOT 表修改或函数劫持 |

### 学习建议

1. **理解堆的结构**：熟练掌握 chunk 的内存布局（prev_size、size、fd、bk 等字段的含义和偏移）
2. **动手实践**：通过 CTF 题目（如经典的 unlink 题目）实际练习利用过程
3. **调试分析**：使用 GDB + pwndbg/gef 动态调试，观察 unlink 前后的内存变化
4. **版本差异**：注意不同 glibc 版本中 unlink 检查机制的差异
5. **结合其他技术**：unlink 通常不是独立使用的，需要结合堆溢出、GOT 表劫持、libc 泄漏等技术形成完整的利用链

### 关键公式速查

```
早期 unlink 任意写：
  FD->bk = BK  →  *(target_addr) = expect_value
  BK->fd = FD  →  *(expect_value + 8) = target_addr - 12

现代 unlink fake chunk 构造：
  fake_fd = P - 12  (32位) 或 P - 0x18 (64位)
  fake_bk = P - 8   (32位) 或 P - 0x10 (64位)

校验条件：
  FD->bk == P  →  *(fake_fd + 12) == P  →  *(P - 12 + 12) == P  →  *P == P ✓
  BK->fd == P  →  *(fake_bk + 8)  == P  →  *(P - 8 + 8)  == P  →  *P == P ✓

利用结果：
  *P = P - 12  (32位) 或 *P = P - 0x18 (64位)
  指针 P 被劫持，指向 fake chunk 内部可控区域
```
