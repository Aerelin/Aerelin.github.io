## 一、Double Fetch 简介

**Double Fetch** 从漏洞原理上来说，是一种**内核态与用户态之间的条件竞争**（Race Condition）漏洞。

在内核代码中，当同一份用户空间数据被内核**两次取用**时——第一次用于安全检查，第二次用于实际处理——攻击者可以通过在两次取用之间修改用户空间数据，绕过内核的安全检查，从而触发越界访问、缓冲区溢出等安全问题，最终可能导致**内核崩溃**或**权限提升**。

## 二、前置知识

### 2.1 内核空间与用户空间

在 Linux 等现代操作系统中，虚拟内存地址通常被划分为**内核空间**和**用户空间**：

| 区域 | 说明 | 权限 |
|------|------|------|
| **内核空间** | 负责运行内核代码、驱动模块代码等 | 权限较高（Ring 0） |
| **用户空间** | 运行用户代码，通过系统调用进入内核完成相关功能 | 权限较低（Ring 3） |

内核空间和用户空间之间的隔离是操作系统安全的基础机制之一。用户程序不能直接访问内核空间的数据，必须通过系统调用（syscall）来请求内核服务。

### 2.2 系统调用与数据传递

通常情况下，用户空间向内核传递数据时，内核通过 `copy_from_user()` 等拷贝函数将用户数据**拷贝至内核空间**进行校验及相关处理。这种方式是安全的，因为数据一旦拷贝到内核空间，用户态就无法再修改它。

但在以下情况下，内核可能**不会拷贝数据**，而是直接引用用户空间的指针：

1. **输入数据较为复杂**（如包含嵌套指针的结构体）
2. **性能优化考虑**（避免不必要的内存拷贝）
3. **数据量较大**（拷贝开销过高）

此时，数据暂时保存在用户空间进行后续处理，**存在被其他恶意线程篡改的风险**。

### 2.3 条件竞争（Race Condition）

条件竞争是指多个线程/进程并发访问共享资源时，程序的执行结果依赖于线程调度的时序。如果内核在检查数据和使用数据之间存在时间窗口，攻击者就可以利用这个窗口修改数据，使得**内核验证通过的数据与实际使用的数据不一致**。

## 三、Double Fetch 漏洞原理

### 3.1 漏洞本质

Double Fetch 漏洞的核心在于：内核代码对同一份用户空间数据进行了**两次读取（fetch）**：

1. **第一次 Fetch（1st Fetch）**：内核取用数据进行**安全检查**，如缓冲区大小检查、指针可用性验证等
2. **第二次 Fetch（2nd Fetch）**：内核取用数据进行**实际处理**

在两次取用之间，另一个用户态线程可以**创造竞争条件**，对已通过检查的用户态数据进行篡改。当内核第二次取用数据时，拿到的是被修改后的恶意数据，从而导致：

- **访问越界**（Out-of-Bounds Access）
- **缓冲区溢出**（Buffer Overflow）
- **类型混淆**（Type Confusion）
- **空指针解引用**（NULL Pointer Dereference）

最终可能导致**内核崩溃（Kernel Panic）**或**权限提升（Privilege Escalation）**。

### 3.2 典型攻击场景

一个典型的 Double Fetch 漏洞原理如下：

1. 一个用户态线程准备数据并通过系统调用进入内核
2. 该数据在内核中有**两次被取用**：
   - 内核**第一次**取用数据进行安全检查（如缓冲区大小、指针可用性等）
   - 检查通过后，内核**第二次**取用数据进行实际处理
3. 在两次取用数据之间，另一个用户态线程可**创造竞争条件**，对已通过检查的用户态数据进行篡改
4. 在真实使用时造成**访问越界**或**缓冲区溢出**，最终导致内核崩溃或权限提升

### 3.3 攻击流程图

```
时间轴 ─────────────────────────────────────────────────────────→

Kernel Space:    [entry] ──→ [1st fetch (check)] ──→ [2nd fetch (real use)]
                      ↑              ↑                        ↑
                      |              |                        |
User Space:           |         ┌────┴────              ┌────┴────┐
                      |         │         │              │         │
                  [prepare data]  [user data] ◄──────────┘         │
                      |         │         │                        │
                  [clone] ──────┘         │                        │
                      |                   │                        │
                  [syscall] ──────────────┘                        │
                      |                                            │
                  [malicious update] ──────────────────────────────┘
```

**流程说明：**

1. **prepare data**：用户态线程准备合法的数据
2. **clone**：克隆出一个新线程，用于后续的恶意修改
3. **syscall**：通过系统调用将数据传递给内核
4. **entry**：内核进入系统调用处理函数
5. **1st fetch (check)**：内核第一次读取用户数据进行安全检查（通过）
6. **malicious update**：恶意线程在检查通过后、实际使用前修改用户空间数据
7. **2nd fetch (real use)**：内核第二次读取用户数据时，拿到的是被篡改的恶意数据

## 四、Double Fetch 利用方法

### 4.1 利用思路

Double Fetch 漏洞的利用关键在于**精确控制竞争时序**，使得恶意修改恰好发生在内核第一次检查和第二次使用之间。

**利用步骤：**

1. **识别漏洞点**：找到内核代码中对用户空间数据进行两次读取的位置
2. **构造恶意数据**：准备一份能通过第一次检查的合法数据，以及一份能触发漏洞的恶意数据
3. **创建竞争线程**：使用多线程（如 `clone()` 系统调用）创建专门用于修改数据的线程
4. **竞争窗口控制**：通过大量循环和精确的时序控制，使修改操作落在两次 fetch 之间的窗口内
5. **触发漏洞**：反复尝试直到竞争成功，实现越界访问或缓冲区溢出

### 4.2 竞争窗口控制

竞争窗口的控制是 Double Fetch 利用的难点。常用技术包括：

#### 4.2.1 循环竞争（Brute Force Racing）

```c
// 主线程：不断发起系统调用
while (1) {
    // 设置合法数据
    setup_legitimate_data();
    // 发起系统调用
    ioctl(fd, CMD, &user_data);
}

// 竞争线程：不断修改数据
while (1) {
    // 修改为恶意数据
    modify_to_malicious_data();
    // 短暂延迟后恢复合法数据
    usleep(small_delay);
    restore_legitimate_data();
}
```

#### 4.2.2 增大竞争窗口

- **系统负载控制**：通过 CPU 密集型任务增加系统负载，拉长内核调度延迟
- **中断注入**：利用 perf_event 等机制触发内核中断，扩大时间窗口
- **CPU 亲和性绑定**：将竞争线程绑定到不同 CPU 核心，增加并发概率

#### 4.2.3 精确时序控制

- 使用 `sched_setaffinity()` 控制线程的 CPU 亲和性
- 使用 `nice()` 调整线程优先级
- 利用 `madvise()` 配合 `MADV_DONTNEED` 触发缺页中断来扩大窗口

### 4.3 利用示例代码框架

以下是一个 Double Fetch 漏洞利用的伪代码框架：

```c
#include <stdio.h>
#include <stdlib.h>
#include <pthread.h>
#include <sys/ioctl.h>
#include <unistd.h>

// 用户空间共享数据结构
struct user_data {
    char *buffer;
    size_t size;
    int flag;
};

struct user_data shared_data;
int fd;  // 设备文件描述符

// 竞争线程：不断修改共享数据
void *racing_thread(void *arg) {
    char *malicious_buffer = malloc(0x1000);  // 恶意大缓冲区
    memset(malicious_buffer, 'A', 0x1000);

    while (1) {
        // 修改为恶意数据（绕过大小检查）
        shared_data.size = 0x1000;  // 原始检查通过的大小
        shared_data.buffer = malicious_buffer;

        // 极短延迟后恢复
        shared_data.size = 0x10;  // 合法大小
        shared_data.buffer = malloc(0x10);
    }
    return NULL;
}

int main() {
    fd = open("/dev/vulnerable_device", O_RDWR);

    // 初始化合法数据
    shared_data.buffer = malloc(0x10);
    shared_data.size = 0x10;
    shared_data.flag = 1;

    // 创建竞争线程
    pthread_t thread;
    pthread_create(&thread, NULL, racing_thread, NULL);

    // 主线程不断发起 ioctl 调用
    while (1) {
        ioctl(fd, VULNERABLE_CMD, &shared_data);
    }

    return 0;
}
```

## 五、实际案例分析

### 5.1 CVE-2016-6516（tty 竞态条件）

Linux 内核 tty 子系统中的一个 Double Fetch 漏洞。内核在 `tioclinux()` 函数中两次读取用户空间的结构体数据，第一次检查参数合法性，第二次使用参数执行操作。攻击者通过竞争修改参数，实现权限提升。

### 5.2 CVE-2010-4258（Full-Nelson）

Linux 内核 `do_compat_setsockopt()` 函数中的 Double Fetch 漏洞。内核在设置 socket 选项时，先检查用户提供的选项长度，然后再次读取该长度来分配内存。竞争修改长度值可导致内核堆溢出。

### 5.3 漏洞模式总结

| 特征 | 描述 |
|------|------|
| **触发条件** | 内核两次读取同一用户空间数据 |
| **攻击面** | ioctl、setsockopt、fcntl 等系统调用 |
| **竞争方式** | 多线程并发修改用户空间共享数据 |
| **危害** | 内核崩溃、信息泄露、权限提升 |
| **利用难度** | 中高（需要精确的时序控制） |

## 六、防御与修复方案

### 6.1 内核侧修复

#### 6.1.1 一次性拷贝到内核空间

最根本的修复方式是在系统调用入口处，将用户空间数据**一次性完整拷贝**到内核空间，后续所有操作都基于内核空间的副本：

```c
// 修复前（存在 Double Fetch）
if (copy_from_user(&size, &user_ptr->size, sizeof(size)))
    return -EFAULT;
if (size > MAX_SIZE)
    return -EINVAL;
// 第二次读取 —— 危险！
if (copy_from_user(buffer, user_ptr->buffer, size))
    return -EFAULT;

// 修复后（安全）
struct kernel_data kdata;
if (copy_from_user(&kdata, user_ptr, sizeof(kdata)))
    return -EFAULT;
// 后续所有操作使用 kdata，不再访问用户空间
if (kdata.size > MAX_SIZE)
    return -EINVAL;
process_data(kdata.buffer, kdata.size);
```

#### 6.1.2 使用 `get_user()` 安全宏

对于简单数据类型的读取，使用内核提供的 `get_user()` 宏，它内部会处理访问异常：

```c
int val;
if (get_user(val, user_ptr))
    return -EFAULT;
// 使用 val 而不是再次从 user_ptr 读取
```

#### 6.1.3 SMAP/SMEP 保护

- **SMAP（Supervisor Mode Access Prevention）**：禁止内核直接访问用户空间内存，强制使用 `copy_from_user()` 等安全函数
- **SMEP（Supervisor Mode Execution Prevention）**：禁止内核执行用户空间代码

开启 SMAP 后，内核无法直接解引用用户空间指针，从硬件层面阻止了 Double Fetch 攻击。

### 6.2 缓解措施

| 措施 | 说明 |
|------|------|
| **开启 SMAP** | 硬件级防护，阻止内核直接访问用户空间 |
| **开启 KASLR** | 内核地址空间布局随机化，增加利用难度 |
| **减少竞争窗口** | 在内核代码中减少两次 fetch 之间的操作 |
| **数据完整性校验** | 在第二次使用前重新校验数据 |
| **使用内核副本** | 始终基于内核空间的数据副本进行操作 |

## 七、总结

### 核心要点

1. **Double Fetch 的本质**：内核态与用户态之间的条件竞争漏洞
2. **漏洞成因**：内核两次读取用户空间数据，第一次用于检查，第二次用于实际处理
3. **攻击方式**：恶意线程在两次读取之间修改用户空间数据，绕过安全检查
4. **危害**：可导致内核崩溃、信息泄露、权限提升
5. **修复方案**：将用户数据一次性拷贝到内核空间，避免多次读取用户空间数据

### 与其他漏洞的关系

| 漏洞类型 | 与 Double Fetch 的关系 |
|----------|----------------------|
| **TOCTOU** | Double Fetch 是 TOCTOU（Time-of-Check to Time-of-Use）在内核场景下的具体表现 |
| **UAF** | 都涉及时序问题，但 UAF 关注内存生命周期，Double Fetch 关注数据一致性 |
| **竞态条件** | Double Fetch 是竞态条件的一种特殊形式，特指内核-用户空间边界 |

### 学习建议

1. 理解 Linux 内核空间与用户空间的内存模型
2. 掌握系统调用中数据传递的机制（`copy_from_user`、`get_user` 等）
3. 学习多线程编程和竞争条件的原理
4. 分析实际 CVE 案例，理解漏洞的发现和利用过程
5. 关注内核安全机制（SMAP、SMEP、KASLR）的发展
