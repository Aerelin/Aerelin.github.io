## 二、Signal 机制介绍

### 2.1 Signal 机制基本概念

Signal 机制是类 Unix 系统中进程之间相互传递信息的一种方法。一般我们也称其为**软中断信号**，或者**软中断**。

- 进程之间可以通过系统调用 `kill` 来发送软中断信号
- 信号机制是操作系统提供的一种异步事件通知机制
- 常见的信号包括 `SIGINT`（Ctrl+C）、`SIGSEGV`（段错误）、`SIGALRM`（定时器）等

### 2.2 Signal 处理流程

Signal 机制的常见处理步骤如下图所示：

```
User Process ──────────────────────────────────────────────► Time
    │
    │  ① 进程正常运行
    │       │
    │       ▼
    │  ─────────────┐
    │  │ Kernel Level │  内核接收信号
    │  │ ucontext save│  保存进程上下文（所有寄存器压入栈中）
    │  └─────────────┘
    │       │
    │       ▼
    │  ② 跳转到 Signal Handler（用户态）
    │  ┌─────────────┐
    │  │Signal Handler│  执行用户注册的信号处理函数
    │  └─────────────┘
    │       │
    │       ▼
    │  ──────────────┐
    │  │ Kernel Level  │  内核执行 sigreturn
    │  │ucontext restore│  恢复之前保存的上下文
    │  ──────────────┘
    │       │
    │       ▼
    │  ④ 进程恢复执行，回到被中断前的状态
    │
```

**四个关键阶段：**

| 阶段 | 描述 |
|------|------|
| ① | 用户进程正常运行，内核向该进程发送 signal，进程被暂时挂起，进入内核态 |
| ② | 内核为该进程保存上下文（所有寄存器压入栈中），并压入 signal 信息以及指向 `sigreturn` 的系统调用地址，然后跳转到注册过的 signal handler 中处理信号 |
| ③ | Signal handler 执行完毕后，执行 `sigreturn` 代码，内核开始恢复上下文 |
| ④ | 内核将所有压入的寄存器重新 pop 回对应的寄存器，最后恢复进程的执行 |

### 2.3 Signal Frame 结构

内核向某个进程发送 signal 机制时，该进程会被暂时挂起，进入内核态。内核会为该进程保存相应的上下文，主要是将所有寄存器压入栈中，以及压入 signal 信息，以及指向 `sigreturn` 的系统调用地址。

此时栈的结构如下图所示：

```
┌──────────────────┐
│                  │
│     stack        │  ← 用户进程的栈空间
│                  │
├──────────────────┤
│                  │
│    ucontext      │  ← 保存的寄存器上下文
│                  │
├──────────────────┤
│                  │
│    siginfo       │  ← 信号相关信息
│                  │
├──────────────────┤
│  sigreturn       │  ← sp 指向此处
└──────────────────┘
```

> **Signal Frame** = `ucontext` + `siginfo` 这一段

**关键要点：**

- 这一部分是在**用户进程的地址空间**中的
- 之后会跳转到注册过的 signal handler 中处理相应的 signal
- 因此，当 signal handler 执行完之后，就会执行 `sigreturn` 代码

### 2.4 x64 架构下的 Signal Frame

对于 Signal Frame 来说，不同架构会有所区别。以下是 **x64 架构**下的 Signal Frame 结构：

| 偏移 | 左列字段 | 右列字段 |
|------|---------|---------|
| 0x00 | `rt_sigreturn` | `uc_flags` |
| 0x11 | `&uc` | `uc_stack.ss_sp` |
| 0x20 | `uc_stack.ss_flags` | `uc_stack.ss_size` |
| 0x30 | `r8` | `r9` |
| 0x40 | `r10` | `r11` |
| 0x50 | `r12` | `r13` |
| 0x60 | `r14` | `r15` |
| 0x70 | `rdi` | `rsi` |
| 0x80 | `rbp` | `rbx` |
| 0x90 | `rdx` | `rax` |
| 0xA0 | `rcx` | `rsp` |
| 0xB0 | `rip` | `eflags` |
| 0xC0 | `cs / gs / fs` | `err` |
| 0xD0 | `trapno` | `oldmask (unused)` |
| 0xE0 | `cr2 (segfault addr)` | `&fpstate` |
| 0xF0 | `_reserved` | `sigmask` |

**Signal handler 返回后的恢复过程：**

1. 内核执行 `sigreturn` 系统调用
2. 为该进程恢复之前保存的上下文
3. 包括将所有压入的寄存器，重新 pop 回对应的寄存器
4. 最后恢复进程的执行

**系统调用号：**

| 架构 | `sigreturn` 系统调用号 |
|------|----------------------|
| 32 位 | 77 |
| 64 位 | 15 |

### 2.5 Signal Frame 的关键安全特性

仔细回顾一下内核在 signal 信号处理过程中的工作，我们可以发现，内核主要做的工作就是为进程**保存上下文**，并且**恢复上下文**。这个主要的变动都在 Signal Frame 中。

**但是需要注意的是：**

> **Signal Frame 被保存在用户的地址空间中，所以用户是可以读写的。**

由于内核与信号处理程序无关（kernel agnostic about signal handlers），它并不会去记录这个 signal 对应的 Signal Frame。所以当执行 `sigreturn` 系统调用时，此时的 Signal Frame **并不一定是之前内核为用户进程保存的 Signal Frame**。

**这就是 SROP 的基本利用原理出现的地方。**

## 三、SROP（Signal Return-Oriented Programming）

### 3.1 SROP 基本原理

SROP 的核心思想：

1. 攻击者可以控制用户进程的栈
2. 攻击者可以**伪造一个 Signal Frame**
3. 当系统执行完 `sigreturn` 系统调用之后，会执行一系列的 pop 指令以便于恢复相应寄存器的值
4. 当执行到 `rip` 时，就会将程序执行流指向 syscall 地址
5. 根据相应寄存器的值，此时便会得到一个 shell

### 3.2 基础 SROP 攻击：获取 Shell

以 64 位为例，伪造的 Signal Frame 如下：

```
偏移    字段              值
─────────────────────────────────────
0x00    rt_sigreturn      uc_flags
0x11    &uc               uc_stack.ss_sp
0x20    uc_stack.ss_flags uc_stack.ss_size
0x30    r8                r9
0x40    r10               r11
0x50    r12               r13
0x60    r14               r15
0x70    rdi = &"/bin/sh"  rsi
0x80    rbp               rbx
0x90    rdx               rax = 59 (execve)
0xA0    rcx               rsp
0xB0    rip = &syscall    eflags
0xC0    cs / gs / fs      err
0xD0    trapno            oldmask (unused)
0xE0    cr2 (segfault addr) &fpstate
0xF0    _reserved         sigmask
```

**攻击流程：**

1. 攻击者伪造 Signal Frame，设置 `rax = 59`（execve 系统调用号）、`rdi = &"/bin/sh"`、`rip = &syscall`
2. 触发 `sigreturn` 系统调用（调用号为 15）
3. 内核从栈上读取伪造的 Signal Frame，恢复寄存器
4. 寄存器恢复后：`rax = 59`，`rdi` 指向 `"/bin/sh"`，`rip` 指向 syscall 指令
5. 执行 `execve("/bin/sh", 0, 0)`，获得 shell

### 3.3 链式 SROP：连续函数调用

上面的例子中，我们只是单独地获得一个 shell。有时候，我们可能会希望执行一系列的函数。我们只需要做两处修改即可控制栈指针：

**关键修改：**

- 把原来 `rip` 指向的 `syscall` gadget 换成 `syscall; ret` gadget
- 这样当每次 syscall 返回的时候，栈指针都会指向下一个 Signal Frame
- 因此就可以执行一系列的 `sigreturn` 函数调用

**链式调用示例：socket() → bind() → listen()**

```
Signal Frame 1 (address1)          Signal Frame 2 (address2)          Signal Frame 3 (address3)
┌─────────────────────┐           ┌─────────────────────┐           ┌─────────────────────
│  rt_sigreturn       │           │  rt_sigreturn       │           │  rt_sigreturn       │
│  rax = 41 (socket)  │           │  rax = 49 (bind)    │           │  rax = 50 (listen)  │
│  rdi = [family]     │           │  rdi = [fd]         │           │  rdi = [fd]         │
│  rsi = [type]       │           │  rsi = [sockaddr]   │           │  rsi = [backlog]    │
│  rdx = [protocol]   │           │  rdx = [addrlen]    │           │                     │
│  rsp = address2     │           │  rsp = address3     │           │  rsp = address4...  │
│  rip = &(syscall;ret)│          │  rip = &(syscall;ret)│          │  rip = &(syscall;ret)│
└─────────────────────┘           └─────────────────────           └─────────────────────┘
         │                                │                                │
         ▼                                ▼                                ▼
    socket()                          bind()                          listen()
```

**流程说明：**

1. 第一个 Signal Frame 执行 `socket()` 系统调用，返回后将 `rsp` 指向第二个 Signal Frame 的地址
2. 第二个 Signal Frame 执行 `bind()` 系统调用，返回后将 `rsp` 指向第三个 Signal Frame 的地址
3. 第三个 Signal Frame 执行 `listen()` 系统调用
4. 以此类推，可以链式执行任意数量的系统调用

### 3.4 使用 pwntools 实现 SROP

在目前的 pwntools 中已经集成了对于 SROP 的攻击支持。

**代码示例：**

```python
from pwn import *

context.arch = "amd64"

# 创建 SigreturnFrame 对象
sigframe = SigreturnFrame()

# 设置寄存器值
sigframe.rax = 59          # execve 系统调用号
sigframe.rdi = '/bin/sh'   # 第一个参数：程序路径
sigframe.rdx = 0           # 第三个参数：环境变量（NULL）
sigframe.rsi = 0           # 第二个参数：argv（NULL）
sigframe.rip = syscall     # 指向 syscall 指令的地址

# 这样即可获得一个可以 getshell 的 SigFrame
payload = bytes(sigframe)
```

**说明：**

- `SigreturnFrame()` 会自动生成符合 x64 架构的 Signal Frame 结构
- 只需设置关键寄存器即可，其他字段会使用默认值
- `bytes(sigframe)` 将 SigreturnFrame 对象序列化为字节串，可直接作为 payload 发送

## 四、总结与学习要点

### 核心知识点

| 知识点 | 要点 |
|--------|------|
| Signal 机制 | 类 Unix 系统的软中断信号机制，用于进程间通信 |
| Signal Frame | 内核保存的进程上下文，包含所有寄存器值，存储在用户地址空间 |
| sigreturn 调用号 | 32 位为 77，64 位为 15 |
| SROP 原理 | 利用 Signal Frame 在用户空间可读写的特点，伪造 Signal Frame 控制寄存器 |
| 链式 SROP | 使用 `syscall; ret` gadget 实现多个 Signal Frame 的连续执行 |
| pwntools 支持 | `SigreturnFrame()` 类简化了 SROP 攻击的构造过程 |

### 利用条件

1. 攻击者能够控制用户进程的栈
2. 能够触发 `sigreturn` 系统调用（调用号 15）
3. 存在可用的 `syscall` 或 `syscall; ret` gadget

### 防御思路

- 限制栈的可写性（NX/DEP）
- 使用 SECCOMP 过滤 `sigreturn` 系统调用
- 栈 Canary 检测栈溢出
- ASLR 增加 gadget 定位难度
